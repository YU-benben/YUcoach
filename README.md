# YUcoach · 短跑跑姿分析系统

> 教练用手机拍下运动员的短跑视频，上传到 App，
> 系统自动提取人体骨骼、计算运动学指标、与可查证的参考区间对比，
> 输出带出处标注的结论和可执行的训练处方。

| 项 | 值 |
|---|---|
| 状态 | **可运行**（分析链路 + App 已打通） |
| 交付形态 | 安卓 App（Flutter）+ 电脑端分析服务（Python） |
| 测试 | 141 个后端测试 + 74 个 App 测试，21 道质量门禁 |
| 目标客户 | 训练队（中学 / 大学 / 体校 / 俱乐部青训） |

## 一、五分钟跑起来

### 前置

**环境在项目内的 `.venv\`（Python 3.13）**，不再依赖系统 PATH 里的 python。

```powershell
.\.venv\Scripts\python.exe -c "import torch; print(torch.cuda.is_available())"   # 需要 True
```

没有 CUDA 的话，姿态提取会慢 60 倍以上，这条路走不通。

> ⚠️ **`pip install torch` 从 PyPI 装的是 CPU 版**，装完不报错、只是慢 60 倍。
> CUDA 版必须从 PyTorch 官方源装，且**版本要选对索引**：
>
> | 索引 | 可用 torch | 说明 |
> |---|---|---|
> | `cu124` | 最高 **2.6.0** | 装 2.14 会静默退回 CPU 版 |
> | **`cu126`** | **含 2.14.1** | ✅ 本项目用这个 |
>
> 重建环境：
>
> ```powershell
> py -3.13 -m venv --copies .venv
> .\.venv\Scripts\python.exe -m pip install -r requirements.txt
> # torch 单独装（走官方源，不能用 PyPI）
> .\.venv\Scripts\python.exe -m pip install torch==2.14.1 torchvision==0.29.1 `
>   --index-url https://download.pytorch.org/whl/cu126
> ```
>
> **不要装 `jsonschema`。** 装了会让契约门 G2 改走另一条校验路径
> （[check_contracts.py](scripts/check_contracts.py) 第 549 行），
> 而项目一直用的是内置 `MiniValidator` —— 那条路径是在没装 jsonschema 的
> 环境下验证过的。装了反而会因 `$ref` 解析差异报错。

```powershell
cd D:\YUcoach
```

> 而手机那侧只会显示"连接超时"，看不出原因。

## 一之二、接口与会员体系

### 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/health` | 服务与引擎状态 |
| `POST` | `/api/auth/register` | 注册（用户名 2–24 字，密码 ≥6 位） |
| `POST` | `/api/auth/login` | 登录，返回账号信息（**不含密码**） |
| `POST` | `/api/profile` | 改昵称 / 身份 / 头像（**不能改会员等级**） |
| `POST` | `/api/redeem` | 用兑换码升级 |
| `POST` | `/api/admin/codes` | 生成兑换码（**仅管理员**） |
| `POST` | `/api/videos` | 上传视频 → `video_id` |
| `POST` | `/api/analyze` | 提交分析（**需登录，消耗一次额度**） |
| `GET` | `/api/jobs/<id>` | 查询进度 / 取报告 |
| `GET` | `/api/reports/<id>` | 只取报告 JSON |
| `GET` | `/keyframes/<任务ID>/<文件名>` | 关键帧图片 |

### 会员与额度

| 等级 | 额度 |
|---|---|
| 普通用户 | 10 次（一次性） |
| 普通会员 | 100 次/月 |
| 高级会员 | 500 次/月 |
| 管理员 | 不限（**对外显示为高级会员**） |

> **训练计划不在额度体系里。** 它是所有人免费的本地功能，
> 不消耗额度，也不因为等级低而被限制。所以它不作为任何等级的权益 ——
> 入口在「我的 → 训练」，独立成栏并标着「免费」。
>
> 这三处必须一致（服务端 `tier_has_plan` 恒为 False、App 独立入口、
> 套餐表不列出它）。曾经把它写成高级会员权益，免费用户看到
> 「不含训练计划功能」就以为自己用不了 —— 而其实一直能用。

**额度由服务端裁定，App 只显示结果。** 会员状态存在服务端的账号文件里，
客户端无法通过改本地数据提权 —— 这类校验放在客户端等于没有。

额度按自然月自动重置。**不用定时任务**：服务没开时定时任务不会跑，
重置就会漏。改成"每次访问时比对周期"，跨月即清零。

### 管理员账号

首次启动自动创建。**账号密码通过环境变量配置**，不写死在源码里：

```powershell
$env:YUCOACH_ADMIN_USER     = "你的管理员账号"
$env:YUCOACH_ADMIN_PASSWORD = "你的密码"
python -m backend.server.app --port 8770
```

密码以 `salt$sha256` 形式存进 `.cache/accounts.json`，**不存明文**。
原因：服务端代码可能被分享、备份、或传到别处，而很多人习惯复用密码 ——
哈希能防止一次泄漏扩散到别的系统。

> ⚠️ **安全边界（必须知情）**
>
> 这是单机、无数据库的简化实现。密码哈希挡的是"密码被直接读到"，
> **挡不住**能读写 `.cache/accounts.json` 的人改会员等级。
> 真要上线需要：数据库 + 会话令牌 + 权限校验中间件。
>
> ⚠️ 删掉 `.cache/` 会**连同所有账号和兑换码一起删掉**。

### 兑换码

**为什么不接真实支付**：微信 / 支付宝需要企业资质 + 商户号，
个人开发者做不到。

兑换码是**能真实运作**的替代方案 —— 你按需生成卡密发给用户，
用户在 App 里输入即可升级。首次启动会生成一批演示码打印在控制台。

管理员生成新码：

```powershell
# 登录拿到账号后，用管理员账号调用
curl -X POST http://127.0.0.1:8770/api/admin/codes `
  -H "Content-Type: application/json" `
  -d '{"username":"管理员账号","tier":"premium","count":10}'
```

## 二、现在能做什么、不能做什么

### ✅ 已经能用

| 能力 | 说明 |
|---|---|
| 完整分析链路 | 解码 → 帧率校验 → 姿态提取 → 20 个指标 → 规则引擎 → 报告 |
| 20 个运动学指标 | 侧面 14 项 + 额状面 6 项，全部实现 |
| 帧率独立校验 | 不信容器声明的帧率，三种方法交叉验证 |
| 镜头运动检测 | 判定固定/轻微/强跟随，位移类指标按此拦截 |
| 参考尺度换算 | 分道线优先，退回身高推算 |
| 相位划分与事件检测 | 触地、支撑中期、离地、腾空最高 |
| **关键帧图片** | 骨骼线 + 角度弧 + 尺度条，自动挑最有代表性的几帧 |
| **姿态提取** | 解码 → 帧率校验 → 姿态提取 → 20 个指标 → 规则引擎 → 报告 |
| **拍摄质量检查** | 分析前先判素材是否合格，不合格就建议重拍 |
| 规则引擎 | 4 条规则，**标准值强制要求出处** |
| App 端 | 注册登录、资料编辑（头像 / 昵称 / 身份）、运动员管理、上传、进度、报告、历史记录、训练计划日历、浅色/深色主题 |
| 服务端 | 零依赖 HTTP 服务，账号与会员体系，兑换码，路径穿越防护，防火墙自检 |

### ⚠️ 已知短板（诚实列出）

| 短板 | 影响 | 现状 |
|---|---|---|
| **足部点默认仍是几何推导** | 触地/腾空时间不可靠 | **已有解**：`--estimator rtm` 用 Halpe26 出实测趾尖/足跟（[docs/14](docs/14-关键点模型选型对照表.md) §9）。默认仍走 yolo，换模型要显式指定 |
| **标准值只有 9/20 有出处** | 大部分指标只报数值不下结论 | 刻意留空，见 §六 |
| **蹲踞式起跑识别出错** | 起跑姿势的关键点会错 | ⚠️ **已用实测确认**：模型对蹲踞姿态检出率低，只检到远处的直立行人（[docs/14](docs/14-关键点模型选型对照表.md) §9.6）。拍摄应避开起跑段 |
| **真实精度未验证** | 不知道误差多大 | 缺合规素材与人工标注基准 |
| **现有素材人物太小** | 只占画面高度 12.6%（应 ≥33%） | 已加拍摄质量检查，会提示重拍 |
| **手机端姿态提取已移除** | 骨架不再在手机上出，必须先连上电脑 | 与"完整分析在电脑上"重复，2026-10-11 删除（省 26.6 MB） |
| **App 账号与服务端账号未打通** | 会员额度在 App 里看不到实时值 | 服务端接口已就绪，接线是下一步 |
| **不支持在线支付** | 只能用兑换码开通 | 个人开发者无法申请支付资质，见 §一之二 |
| **分步用时表未做** | 只能看关键帧的步序号，没有逐步数据表 | 契约字段已有，待实现 |
| **防火墙自检读不到规则** | 启动时显示"状态未能确认" | 读规则需管理员权限，已改为三态输出（不误报），见 §七.3 |

### 手机端姿态推理（已于 2026-10-11 移除）

手机端**曾经**自己跑姿态模型（ONNX），不依赖电脑就能出关键点与骨架图。
现在这套已删除，**骨架提取只在电脑端做**。

**为什么删**：它与"完整分析在电脑上完成"的定位重复，而代价是真实的——
多一套 Dart 实现要维护、多 26.6 MB（模型 + vendored ONNX Runtime）、多 93 条测试。
单人项目少一条线就少一半维护成本。

**删掉后丢掉的两样东西**（如实记录）：

| 丢失的能力 | 说明 |
|---|---|
| **离线可用** | 以前没网络也能出骨架图看姿势；现在必须先连上电脑 |
| **跨语言对拍** | `pose_parity_test.dart` 是唯一防止"Dart 和 Python 解出不同骨架"的机制 |

> 第二点值得记住：那个对拍**抓到过一个真实错误** ——
> Dart 第一版假设模型输出是 0~1 归一化值，实际是 **0~640 的像素值**，
> 所有关键点大了 640 倍。算错不报错，靠肉眼看代码很难发现。
>
> 现在手机端不再解析模型输出，**两边不一致的风险从根上消失了** ——
> 所以这个保护也就不再需要。逻辑上自洽。

**`mobile/lib/pose/` 仍保留 6 个模块**，因为 App 的其他部分还在用：

| 模块 | 谁在用 |
|---|---|
| `pose_types.dart` | 姿态数据类型（`Keypoint` / `PoseFrame` / `PoseSequence`） |
| `angle_catalog.dart` · `angle_selection.dart` | 报告页的角度选择器（`widgets/angle_picker_sheet.dart`） |
| `gait_events.dart` · `smoothing.dart` · `foot_derivation.dart` | 仍有测试覆盖 |

**手机端与电脑端的现行分工**：

| 工作 | 放哪 | 为什么 |
|---|---|---|
| 视频解码与元数据校验 | 手机 | 视频本来就在手机上 |
| 上传 | 手机 | 分片流式上传，内存占用与文件大小无关 |
| 姿态提取 · 指标 · 规则 · 报告 | **电脑** | 只有一份实现，不会出现两套慢慢漂移 |
| 报告展示 · 训练计划 | 手机 | 纯 UI |


### ❌ 永久不做

- 起跑反应时（需专业计时设备）
- 地面反作用力 / 关节力矩（二维视频无法反推）
- **跟踪拍摄下的绝对速度**（画面位移 = 运动员位移 + 镜头位移，单目不可分离）
- 损伤诊断（涉及医疗责任）

## 三、为什么需要合规素材

**现有样例素材是 30 fps，而触地时间只有 80–120 毫秒。**

```
30 fps  →  单帧 33 ms  →  误差 33%   ❌ 毫无意义
120 fps →  单帧 8 ms   →  误差 8%    ✅ 可用
```

所以系统在 30 fps 素材上会**拒绝给出所有指标数值**，只报"数据不足"。

**这不是 bug，是这个项目最重要的设计决定**：一个看起来合理的错数字，
比"测不出来"危险得多 —— 教练会照着错数字改动作。

### 拍摄标准

```
侧面固定机位 · 手机慢动作（120fps 或 240fps）
运动员占画面高度 1/3 以上 · 分道线入画 · 3–5 秒即可
```

### 关于"生成物都在项目内"

所有运行时文件都落在 `YUcoach/` 内部，**不散到项目外**。

实现方式是 `backend/paths.py` 作为**路径的唯一事实源**：
要改路径只改这一个文件。门禁 G0 会检查每个目录都确实在项目内。

> **例外：机器级共享缓存不在项目内，这是刻意的。**
>
> `pip` 的包缓存、Gradle 的构建缓存是**这台机器上所有项目共用**的
> （分别约 5.5 GB 和 4.5 GB），它们不是 YUcoach 的生成物。
> 搬进项目会让目录从 2.5 GB 涨到 12 GB，且失去跨项目复用。
>
> 判断标准：**删掉它只影响 YUcoach，就是项目生成物。**

## 五、12 条设计原则

> **这 12 条是宪法。任何具体约定与它们冲突时，改约定，不改原则。**

| # | 原则 | 违反的后果 |
|---|---|---|
| P1 | **事实与判断分离** | 算法升级会污染结论，无法追溯 |
| P2 | **不确定性是一等公民** | 教练拿到假数字且无从察觉 |
| P3 | **全链路可追溯** | 被质疑时无法回答"这个结论哪来的" |
| P4 | **契约与实现解耦** | 换模型要重写前端 |
| P5 | **阶段绑定** | 同一数字在不同阶段含义相反 |
| P6 | **视角绑定** | 矢状面与额状面混淆，结论全错 |
| P7 | **以帧为时间基准** | 浮点误差累积；帧率不可信时无法纠正 |
| P8 | **不信任容器元数据** | 帧率错一倍，时间指标静默全错 |
| P9 | **拍摄规范是上游** | 在垃圾输入上做精细算法 |
| P10 | **宁可不说，不可说错** | 沉默被误读为"没问题" |
| P11 | **诚实的能力边界** | 给错数字比不给危害更大 |
| P12 | **一切版本化** | 数值变了说不清原因 |

## 六、标准值：这个项目最严的一条规矩

> ## 任何写入标准值库的数字，必须能指向一份可查证的原始文献，且记录页码或图表号。
> ## 查不到就留空。
> ## 留空意味着该指标只输出测量值，不做偏离判断。

### 为什么这么严

**标准值编造是全项目唯一无法通过测试发现的错误类型。**

| 错误类型 | 怎么发现 |
|---|---|
| 指标算错 | 对比合成数据的解析解 |
| 契约写错 | Schema 校验 |
| 事件检测错 | 抗噪性测试 |
| **标准值编造** | **没有任何自动检测手段** |

而后果是**系统性**的：所有运动员都被报同一个问题，数字看起来完全合理。

### 当前状态：5/20 有可用标准值

| 指标 | 区间 | 出处 |
|---|---|---|
| `step_frequency` | 259.4–283.8 步/分 | Štuhec 2023，柏林世锦赛决赛选手 |
| `knee_angle_touchdown` | 133.1–166.7° | IAAF 2017，Table 10/11 |
| `ground_contact_time` | 85–118 ms | IAAF 2017，Table 17 |
| `flight_time` | 125–145 ms | IAAF 2017，Table 17 |
| `step_length_relative` | 1.08–1.20 | IAAF 2017，Figure 25 |

其余 15 个在待补清单里，逐个记录"**需要什么数据、去哪里找、为什么现在没有**"。

```powershell
python scripts\check_standards.py     # 列出可用与待补
```

### 三道机械防线

| 防线 | 拦住什么 |
|---|---|
| `source.locator` 必须非空 | 凭印象编造 |
| `view` / `phase` 必须与指标匹配 | 跨视角、跨阶段套用 |
| `plausible_range` 生理可信范围 | 从文献抄错行 |

> 第三条是真的拦住过东西：从 IAAF 报告提取躯干角时，
> PDF 表格的列标题在提取中丢失，换算出 61–68° 的前倾角 ——
> 而短跑途中跑是 5–15°。这个值在"0–180° 的合法角度"里毫无问题，
> 只有对照"人跑起来躯干能摆成什么样"才能发现。
>
> **口径未核实的数值不入库**，记录在 `data/standards/iaaf_2017_100m.yaml`
> 的 `rejected` 段，连同完整理由。

### 怎么做验证（因为没有真实基准）

**问题**：没有人工标注，怎么知道指标算得对？

**做法一：合成数据 + 解析解**

自己造姿态序列，姿态由公式生成 —— 所以理论值已知。

```
步频     构造 272.7  →  算出 271.9   误差 0.3%
躯干前倾 构造 8.0°   →  算出 8.01°   误差 0.1%
骨盆侧倾 构造 ±4°    →  sd=2.78（理论 2.83）
```

**做法二：噪声敏感性分析**

给合成数据注入已知幅度的噪声，看指标偏多少。给出的是**误差上界**。

```
3 像素噪声下（YOLOv8-pose 的典型水平）：
  trunk_lean            0.03°
  hip_angle_toeoff      0.20°
  knee_angle_touchdown  0.60°
```

**这两者都证明不了真实精度** —— 合成数据没有遮挡、运动模糊、
透视变形，也没有模型的系统性偏差。要验证真实精度，**必须人工标注基准**。

### App 热重载

**现有 APK 不会自动更新。** 要边改边看效果，用：

```powershell
cd mobile
flutter run          # 手机需连数据线并开启 USB 调试
```

跑起来后按 `r` 热重载（1 秒生效），按 `R` 热重启。

> 只改后端 Python 代码的话，**不用重装 App** —— 重启服务即可。
> 改 `data/standards/*.yaml` 同理。

### 加一个指标

1. 在 `docs/03-指标定义.md` 写下定义（公式、依赖、适用视角）
2. 在 `metrics_base.py` 的 `METRIC_SPECS` 里声明（含 `plausible_range`）
3. 在 `metrics.py` 实现函数，注册进 `METRIC_FUNCS`
4. 加测试；`test_every_metric_spec_has_an_implementation` 会守住"不许漏"
5. 如果要做偏差判定，去 `data/standards/` 补**有出处**的标准值

### 加一条规则

在 `rules.py` 的 `RULES` 里加。**规则本身不含数值区间** ——
区间全部来自标准值库，这样补文献时只改 YAML，不会漏改代码。
