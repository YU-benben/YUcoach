## 1. 项目定义

### 1.1 一句话

训练队的教练用手机拍下运动员的短跑视频，上传到 App，系统自动提取人体骨骼、计算运动学指标、与标准值对比，输出**带角度标注的关键帧图**和**可执行的训练指导**。

### 1.2 解决什么问题

教练判断跑姿，目前只有两条路：

| 现状 | 问题 |
|---|---|
| 凭肉眼和经验看 | 高速动作看不清细节；不同教练判断不一致；无法量化对比 |
| 用专业设备（高速相机 + 动作捕捉 + 测力台） | 一套几十万，需要实验室环境，训练队用不上 |

**本项目要做的是中间那条路**：用一部手机 + 一套算法，给出接近专业分析的可用结论。

### 1.3 核心价值主张

> **不是"能测角度"，而是"能告诉教练下一步练什么"。**

市面上已有大量姿态识别工具，绝大多数停留在"画出骨骼线"或"手动逐帧标点测角度"。本项目的差异点：

| # | 差异点 | 具体含义 |
|---|---|---|
| 1 | **短跑专项** | 指标、阶段划分、判定规则全部针对短跑，不做通用健身动作 |
| 2 | **三视角分流** | 侧面 / 正面 / 背面各自测不同的指标，不可混用 |
| 3 | **允许跟踪拍摄** | 承认镜头会跟随运动员移动，并显式处理由此产生的误差 |
| 4 | **阶段化对比** | 与阶段化标准区间比对，不与某个具体运动员逐帧对比 |
| 5 | **可执行结论** | 每条问题直接关联训练处方，含教练现场能喊的口令 |
| 6 | **不确定性可见** | 不可靠的数字显式标注，而不是隐藏或伪装 |

**第 6 条是长期信任的基础。** 运动分析工具最常见的死法是：教练发现某一次数值不对，从此不再相信所有数字。

## 2. 完整工作流

```
①  教练用手机在跑道边拍摄
    ├─ 侧面：站在跑道侧面，镜头跟随运动员移动
    ├─ 正面：站在运动员前方，镜头跟随
    └─ 背面：站在运动员后方，镜头跟随
         ↓
②  在 App 中选择视频文件
    （系统相册 / 文件管理器）
         ↓
③  App 读取视频元数据并做初级校验
    帧率、分辨率、时长、帧数自洽性
         ↓
④  填写采集信息
    运动员 / 测试类型 / 机位距离 / 视角
         ↓
⑤  上传原始文件（不转码、不压缩）
         ↓
⑥  服务端分析
    帧率校验 → 视角识别 → 镜头运动补偿 → 姿态提取
    → 时序平滑 → 指标计算 → 分阶段 → 与标准值对比
    → 规则引擎 → 报告生成
         ↓
⑦  App 查看报告
    关键帧角度图 + 指标对比 + 指导解析 + 训练处方
```

### 2.1 一条关键的设计约束

> **App 不做任何分析。所有计算在服务端。**

理由：

| 理由 | 说明 |
|---|---|
| 视频帧数太多 | 10 秒 240fps = 2400 帧，手机端全流程推理会发热降频 |
| 模型必须能迭代 | 嵌在 App 里意味着每次改模型都要重新发版 |
| 分析是异步的 | 30–60 秒出结果完全可接受，不需要实时 |
| 一人开发 | 端侧 + 服务端两套推理链路会翻倍工作量 |

**App 只做四件事**：选择文件、读取元数据、填写信息、上传与展示。

---

### 2.2 三个角色（不要混淆）

> 本节专门澄清一个常见误解：**"为什么开发阶段需要拍素材"**。

| 角色 | 视频从哪来 | 需要额外做什么 |
|---|---|---|
| **开发者（你）** | 自己拍一小批 | 一次性投入，用于调参与验证 |
| **教练（用户）** | 本来就有的训练视频 | **什么都不用多做**，只是以前存手机里，现在上传 |
| **系统** | 教练上传的每一段 | 自动变成长期数据资产 |

#### 2.2.1 开发阶段为什么需要素材

不是为了"模拟使用"，而是**没有素材无法回答三个问题**：

| 问题 | 没有素材的后果 |
|---|---|
| 算法到底准不准？ | "做完了"只是一句感觉。必须手工标出真实关节位置，与算法输出对比 |
| 参数该调成多少？ | 有效测量窗取 ±20% 还是 ±30%？平滑窗口取 fps/10 还是 fps/8？必须试出来 |
| 改代码有没有搞坏老功能？ | 需要一批固定素材做回归测试 |

**规格**

| 项 | 量 |
|---|---|
| 素材量 | 20 段左右 |
| 时长 | 每段 5–15 秒 |
| 覆盖 | 三种视角 × 多运动员 × 多机位 |
| 拍摄时间 | 半天到一天 |
| 性质 | **一次性**，之后不用再拍 |

**这 20 段是开发资产，不是产品流程的一部分。教练永远不需要知道它存在。**

#### 2.2.2 教练那条线什么都不用多干

```
本来就是训练，本来就会拍视频
        ↓
以前：拍完存在手机里 / 发微信群
现在：拍完在 App 里上传
```

**没有新增任何动作。** App 端的初级校验和拍摄方位选择，是在**消化**教练随手拍的视频，不是在**要求**教练拍得更好。

#### 2.2.3 教练上传的视频是免费的长期资产

| 数据 | 来源 | 价值 |
|---|---|---|
| 原始视频 + 姿态数据 | 每次上传 | 后期微调模型的训练集 |
| 教练的人工修正 | 每次纠正关键帧 | **免费的标注**，质量比自标更高 |
| 队内标准值 | 累计 ≥30 人次 | **别人拿不走的护城河** |

> 上线三个月后的真实数据，比任何自己拍的素材都有价值。
>
> **开发阶段拍 20 段，只是为了让系统能活到那一天。**

## 3. 技术路线

| 环节 | 方案 |
|---|---|
| 客户端 | Flutter（一套代码出安卓，后续可出 Web 教练端） |
| 服务端 | Python + FastAPI |
| 任务队列 | Celery + Redis |
| 姿态模型 | YOLO-pose 系列（YOLOv8/v11-pose）或 RTMPose |
| 推理运行时 | ONNX Runtime + CUDA |
| 数据库 | PostgreSQL |
| 对象存储 | MinIO / S3 兼容 |
| 报告渲染 | 服务端 HTML → PDF |

### 3.1 为什么用 YOLO-pose

| 理由 | 说明 |
|---|---|
| 开源可商用 | 无授权风险 |
| 精度足够 | 短跑侧面姿态的关键点定位可达像素级 |
| 速度合适 | GPU 上处理 2400 帧只需数秒 |
| 可微调 | 后续可用自己积累的数据做迁移学习 |
| 生态成熟 | 导出 ONNX、部署方案都现成 |

**但 YOLO-pose 有一个已知短板**：标准 COCO 17 点模型**没有足部关键点**。而短跑的着地方式判定、离地判定都依赖趾尖位置。

**应对**：本项目采用包含足部的关键点集合（见 `01-术语与命名规范.md` §4），可用 26 点模型（Halpe 格式）或在 YOLO-pose 基础上自训练补足足部点。

## 4. 三个必须正视的技术约束

> 这三条决定了系统"能做什么、不能做什么"。回避它们会导致后期返工。

### 4.1 约束一：镜头跟踪会引入透视误差

**你的拍摄方式**：站在固定位置，镜头跟随运动员移动。这在实战中是必要的（否则运动员会跑出画面），但会带来两个后果：

| 后果 | 说明 |
|---|---|
| 运动员偏离画面中心 | 视线偏斜，投影到画面的角度不等于真实角度 |
| 各帧的误差不一致 | 画面中心的帧误差小，边缘的帧误差大 |

**误差量级**：视线偏斜 15° 时，一个真实 30° 的角度会投影成约 29°，误差约 1°；偏斜 30° 时误差可达 3–4°。

**本项目的处理方式**（详见 `05-模型与算法实现规范.md`）：

1. **定义"有效测量窗"**：只采信运动员处于画面中心 ±20% 区域内的帧
2. **逐帧输出透视误差估计**：不隐瞒，让用户知道哪些帧可信
3. **区分指标对跟踪的敏感度**：角度类基本免疫，位移类必须补偿
4. **在报告里给出拍摄改进建议**：当有效帧不足时，明确告诉教练怎么拍能更好

**不做的事**：不假装镜头没动，不用未经验证的补偿算法硬凑数据。

### 4.2 约束二：跟踪拍摄下无法输出绝对速度

画面里运动员的位移 = 运动员真实位移 + 镜头位移。要分离两者必须做镜头运动估计，而估计结果的精度取决于：

- 背景中是否有足够的静止纹理特征
- 镜头是纯平移还是带旋转（手持必然带旋转）
- 拍摄距离是否恒定

**本项目的处理方式**：

| 指标 | 是否可用 | 依据 |
|---|---|---|
| 关节角度 | ✅ 可用 | 角度对像素尺度不敏感 |
| 触地时间、腾空时间、步频 | ✅ 可用 | 只依赖帧号，与空间无关 |
| 步幅（相对量） | ✅ 可用 | 用运动员自身肢体长度做参考尺度 |
| 步幅（绝对米） | ⚠️ 有条件 | 需画面中可见跑道分道线作为参考 |
| 速度曲线 | ❌ 不输出 | 无法可靠分离镜头运动 |
| 质心绝对位移 | ❌ 不输出 | 同上 |

**这是诚实的能力边界。** 给一个错的速度数字，比不给速度数字危害大得多。

### 4.3 约束三：三种视角测的是不同的东西

| 视角 | 能看到什么 | 看不到什么 |
|---|---|---|
| **侧面** | 矢状面：髋/膝/踝角度、躯干前倾、大腿摆动 | 骨盆旋转、膝内扣、着地宽度 |
| **正面** | 额状面：骨盆倾斜与旋转、膝内外翻、着地宽度、躯干侧倾 | **所有矢状面角度** |
| **背面** | 额状面（同正面）+ 臀中肌控制、足跟外翻 | 同正面 |

> **两种视角的数据不可混用，不可互相替代。**
>
> 用正面视频算"膝关节角"，得到的是完全不同的几何量。

**本项目的处理方式**：视频的视角作为**必填参数**，直接决定哪些指标被计算。见 `03-指标定义.md`。

## 5. 项目范围

### 5.1 做

- 三种视角（侧 / 正 / 背）的短跑视频分析
- 允许镜头跟踪拍摄，并显式处理透视误差
- 六个运动阶段：预备、起动、加速段、过渡段、途中跑、减速段
- 关节角度、时间参数的自动提取
- 与标准区间的对比与偏离度计算
- 带角度标注的关键帧图生成
- 规则驱动的改进建议与训练处方推荐
- 运动员档案与历史记录
- 多队伍账号体系与数据隔离

### 5.2 永久排除（物理上不可靠）

| 项目 | 排除原因 |
|---|---|
| 起跑反应时 | 需专业起跑计时设备 |
| 地面反作用力 / 峰值力绝对值 | 二维视频无法可靠反推 |
| 关节力矩 | 需逆动力学 + 测力台 |
| 跟踪拍摄下的绝对速度 | 无法分离镜头运动（见 §4.2） |
| 实时逐帧反馈 | 延迟与抖动会破坏信任，且训练场景不需要 |
| 损伤诊断 | 涉及医疗责任 |
| 成绩预测 | 需大样本验证，错误代价高 |

### 5.3 暂缓（后期评估）

| 项目 | 暂缓原因 |
|---|---|
| 多机位同步分析 | 复杂度高，单机位未验证前不启动 |
| 自动相机跟随（云台） | 需硬件配合 |
| iOS 客户端 | 目标用户以安卓为主 |
| 与光电门 / GPS 数据融合 | 需外部设备接口 |
| 三维重建 | 二维精度未验证前不做 |

## 6. 成功标准

### 6.1 技术标准

| 指标 | 目标 |
|---|---|
| 关节角度误差 | < 5°（与人工标注金标准对比） |
| 不同机位下的误差稳定性 | 变化 < 3% |
| 事件帧定位误差 | ≤ 1 帧 |
| 单条视频分析耗时 | < 90 秒（10 秒素材，240fps） |
| 报告生成成功率 | > 98% |

### 6.2 产品标准

| 指标 | 目标 | 说明 |
|---|---|---|
| 教练能独立完成上传 | 首次成功率 > 85% | **最重要的可用性指标** |
| 报告被采纳率 | 教练实际执行了至少 1 条建议 | 通过回访确认 |
| 复用率 | 同一教练 4 周内主动使用 ≥ 3 次 | 判断是否真正有用 |
| 素材合格率 | 首次上传合格率 > 70% | 反映引导是否有效 |

> **注意：报告的"准确性"不是产品成功指标，"教练是否照着做"才是。**
>
> 一份 95% 准确但没人看的报告，价值为零。

## 7. 关键假设

> **假设不是事实。** 每条假设都有验证方式与失败后的应对。验证未通过时必须走"失败应对"分支。

| 编号 | 假设 | 验证方式 | 失败后的应对 |
|---|---|---|---|
| A1 | 教练能拍到可用的视频 | 收集 20 段真实训练视频实测 | 加强 App 引导；接受质量分级 |
| A2 | 跟踪拍摄下的角度误差可接受 | 与固定机位对比 | 限定有效测量窗；误差过大则要求固定机位 |
| A3 | 二维角度精度可达 5° 内 | 与人工标注对比 | 引入标定与畸变校正；限定拍摄距离 |
| A4 | 从外部文件能可靠读到帧率与帧数 | 多机型实测 | 降级为"帧率未知"，交服务端判定 |
| A5 | 教练愿意持续使用并付费 | 试用 4 周后访谈 | 调整定位或转向科研工具 |
| A6 | 单人可在合理周期内完成 | 阶段进度跟踪 | 砍功能，保核心链路 |

**A2 是本项目特有的假设。** 其他同类系统都要求固定机位，而本项目允许跟踪拍摄——这意味着我们必须证明"跟踪拍摄下的角度测量仍然可用"。**这一条验证不通过，整个拍摄方案要改。**

## 8. 风险登记

| 编号 | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | 跟踪拍摄导致有效帧不足 | 高 | 高 | 定义有效测量窗；报告给出拍摄改进建议；必要时建议固定机位 |
| R2 | 手机锁不住高帧率录制 | 中 | 中 | 用系统相机慢动作模式，App 只负责上传 |
| R3 | 视频帧率元数据不可信 | 中 | 高 | 三法交叉校验；不通过则拒绝时间类指标 |
| R4 | 无足部关键点致着地判定不准 | 中 | 中 | 用 26 点模型或自训练补足部点 |
| R5 | **教练不持续使用 / 不愿付费** | 中 | **致命** | 早期深度参与；**链路打通后立即验证付费意愿** |
| R6 | 单人开发进度失控 | 高 | 高 | 严格按阶段交付；砍功能保核心链路 |
| R7 | 标准值数据缺失 | 中 | 中 | 查不到就留空，不做偏离判断，不编造数字 |
| R8 | 视频素材版权与数据合规 | 中 | 中 | 明确授权条款；训练用途需单独授权 |

**R5 是唯一"致命"级风险。** 其余风险导致"做不出来"，R5 导致"做出来了但没意义"。

因此有一条硬性要求：**链路打通后必须立刻拿报告去找教练验证，不得等到产品完成。**
