## 1. 一句话结论

**候选模型不是"要不要换"，而是"你早就把评估工具写好了"。**

仓库里已有 [scripts/evaluate_foot_keypoints.py](../scripts/evaluate_foot_keypoints.py)，它回答的正是本表要回答的问题，而且判据设计得比常规做法更严：

> 一个"稳定但系统性错误"的足部点，比"不稳定但无偏"的更危险——它会稳定地给出错误的触地时刻。

**所以本文档的定位从"选型"改为"记录实测结果 + 指出一个必须补的判据"。**

### 2.3 追加诊断（本文档新增）

为判断哪一方更可信，另跑了一次分布统计（368 个足部样本）：

| 量 | 右脚 | 左脚 |
|---|---|---|
| **踝→趾** 中位 | 0.0168（**9.1 px @540**） | 0.0185（**10.0 px**） |
| 踝→趾 范围 | 0.0045 – 0.0245 | 0.0096 – 0.0240 |
| 踝→跟 中位 | 0.0086（4.6 px） | 0.0105（5.7 px） |
| 趾相对踝的方向 | 中位 dy **+0.0162**（在下方）、dx −0.0074 | — |

**关键推算：**

```
期望比值 = 足长/身高 ÷ 躯干长/身高 ≈ 0.15 / 0.30 = 0.5
实测比值 = (踝→趾) / (肩髋中点垂直距离) = 0.90
```

**实测足部关键点跨度约为解剖学期望值的 1.8 倍；而几何推导的脚尖跨度达画面高度 29%，约为期望值的 3.5 倍。**

> ⚠️ **两个数字都不能直接采信**，因为这段素材本身不满足标定条件：
> 运动员仅占画面高度约 13%（要求 50–70%，见 [README](../README.md) §二 已知短板）。
> 目标过小时，像素级关键点的相对误差会被放大，**任何足部关键点的绝对跨度都不可用于结论。**

## 3. 必须补的一条判据（本文档的核心产出）

你原有脚本的四条判据里，**方向性自检很强**（脚尖必须在踝下方——这一条抓"点错关节"很有效），但缺一条**尺度自检**。

### 3.1 缺什么

| 现有判据 | 能抓什么 | 抓不到什么 |
|---|---|---|
| 可见度分布 | 点是否稳定检出 | — |
| 脚尖在踝**下方** | 点错到别的关节 | **足部点塌缩**：趾/跟都贴在踝上，方向仍然正确 |
| 脚跟不低于踝 | 同上 | 同上 |
| 与推导点距离 | 两模型有分歧 | 分不清谁对 |

**"足部点塌缩"是真实存在的失效模式**：模型在足部不清晰时，倾向于把趾与跟预测到踝附近（回归到均值）。此时方向自检 100% 通过，可见度可能也不低，但**足部几何已经失真**——而触地判定恰恰依赖足部的伸展形态。

### 3.2 建议补的判据

```python
# 解剖学尺度自检：足部关键点跨度必须落在物理可能范围内
#   足长 ≈ 0.15 × 身高；躯干(肩中点-髋中点) ≈ 0.30 × 身高
#   => (踝→趾) / 躯干高度 的合理区间约 0.35 – 0.75
ratio = dist(ankle, toe) / torso_height_px
if not (0.35 <= ratio <= 0.75):
    flag_collapsed_or_oversized(frame, side, ratio)
```

**这条判据的价值：它是唯一能发现"足部点稳定但整体失真"的手段。** 与 [docs/02](02-数据标准.md) QC-2「肢长恒定」是同一个思路——用解剖学常数去约束测量结果。

> 建议同时接入 [docs/02](02-数据标准.md) §17 的 QC-2/QC-3 体系，而不是新开一套。

## 6. 换模型的验证清单（必须全做）

> **依据：** [README](../README.md) 记录过两次"算错不报错"的真实事故——
> ① Dart 假设坐标是 0–1 归一化，实际是 0–640 像素 → 关键点大了 640 倍
> ② 框参数又犯一次 → 靠"关键点包围盒 / 框宽 = 0.69"的几何交叉验证才发现
>
> **两次都发生在"换实现"环节。**

| # | 检查 | 手段 | 不通过会怎样 |
|---|---|---|---|
| 1 | 关键点索引核对 | 在标注帧上画出全部点及编号，目视确认 | 膝踝对调 → 角度看似合理但全错 |
| 2 | 坐标量纲确认 | 打印原始输出范围，确认像素还是 0–1 | 640 倍错误（已犯过） |
| 3 | 跨语言对拍 | 重跑 `scripts/pose/gen_pose_fixtures.py` → `mobile/test/pose_parity_test.dart` | Dart 与 Python 结果不一致 |
| 4 | 叠加目视（QC-4） | 骨骼线画回原始帧，重点看足部点 | 系统性错位无法自动发现 |
| 5 | 新旧模型同帧对照 | 同帧跑两模型，比 12 个共有点位移 | 无法区分"新增足部"与"全身挪位" |
| 6 | **足部尺度自检（新增）** | §3.2 的解剖学比值判据 | **足部点塌缩无法被发现** |
| 7 | 左右侧正确性 | 正/背面各测一次 | 分侧统计完全颠倒（[docs/02](02-数据标准.md) §13.2 最易错项） |
| 8 | 合规素材复测 | 用 120 fps、占画面 50–70% 的素材重跑 | 现有 13% 占比的素材无法定论 |

**顺序要求：先做 8，再做 1–7。** 现有素材上的一切足部数值都不能作为结论。

## 7. 执行顺序

```
① 补 §3.2 的解剖学尺度判据进 evaluate_foot_keypoints.py
        ↓
② 用合规素材（120 fps、占画面 50–70%）重跑评估
        ↓
③ 比值落在 0.35–0.75 内 → 接 MediaPipe；否则转 Halpe26（§6 触发条件）
        ↓
④ 写 mediapipe33_to_yu16()，保留 derive_foot_points() 作降级路径
        ↓
⑤ 走完 §6 的 1–7 项
        ↓
⑥ 切换默认模型，更新 VERSIONS 与报告版本号（P12 一切版本化）
```

### 7.1 降级路径不可删（设计约束）

```
实测足部点（模型给了，conf 足够）  → q = Q_CLEAR / Q_UNCERTAIN（按 conf）
推导足部点（模型没给，几何补）      → q = Q_UNCERTAIN（上限，永不 Q_CLEAR）
```

**依据 P2（不确定性是一等公民）**：模型遮挡/出画时必须有降级路径，但降级点不能与实测点同级——否则教练无法知道这次的触地判定是实测还是推的。

### 7.2 不要做的事

| ❌ 不要 | 为什么 |
|---|---|
| 引入 133 点全套 | 100+ 个用不到的点只增加出错面 |
| 删掉 `derive_foot_points()` | 丢失降级路径 |
| 让推导点拿到 `Q_CLEAR` | 违反 P2 |
| 改 `KEYPOINT_NAMES` 的 16 点定义 | 契约已冻结，改了要动 Dart 模型与 8 个 Schema |

#### 怎么让 onnxruntime 用上 GPU（不需要装 CUDA Toolkit）

**问题**：onnxruntime-gpu 需要 cuBLAS / cuDNN，而本机没装 CUDA Toolkit。
`get_available_providers()` 列出了 `CUDAExecutionProvider`，但创建 provider 时
失败并**静默退回 CPU**：

```
Failed to create CUDAExecutionProvider.
Require cuDNN 9.* and CUDA 12.*
```

**根因与解法**：**torch 自带这些 DLL**，就在
`.venv/Lib/site-packages/torch/lib/` 下（`cublasLt64_12.dll`、`cudnn64_9.dll` …）。
Windows 加载器不会自动去那里找，所以只要**把它前置到 PATH** 即可：

```python
import os, torch
torch_lib = Path(torch.__file__).parent / "lib"
os.environ["PATH"] = str(torch_lib) + os.pathsep + os.environ["PATH"]
```

已实现在 `RtmPoseEstimator._prepare_cuda_dlls()`。**不需要单独安装 CUDA Toolkit。**

**版本选择也很关键**：

| onnxruntime-gpu | 要求 |
|---|---|
| 1.31.0 | **CUDA 13** + cuDNN 9 ❌ 本机是 CUDA 12.6 |
| **1.22.0** | **CUDA 12** + cuDNN 9 ✅ 与 torch 自带的 DLL 匹配 |

> ⚠️ **判断 provider 能不能用的唯一可信方式是真建一个 `InferenceSession`
> 然后看 `get_providers()` 的返回值。**
> `ort.get_available_providers()` 只检查 DLL 能否**加载**，
> 不代表 provider 能**创建** —— 实测它列出了 CUDA，而会话实际建在 CPU 上。
> 这个区别会让人以为 GPU 生效了，然后纳闷为什么这么慢。

**opencv 后端不可行的原因**：`mobile`/`venv` 里装的 opencv 是 **CPU 构建**
（`cv2.cuda.getCudaEnabledDeviceCount()` 返回 0，构建信息里 cuda* 模块全部 Unavailable）。
要用 rtmlib 的 `backend='opencv'` + GPU，需要自己编译带 CUDA 的 OpenCV —— 不值得。
