## 1. 优先级不可逆

> **顺序的本质是：**
>
> **先保证「数据是对的」（拍摄 + 标注）→ 再保证「数字是对的」（指标）→ 再保证「话是对的」（规则）→ 最后才考虑「界面好不好看」。**
>
> **反过来做，每一步都要返工。**

| 顺序 | 环节 | 错了的后果 |
|---|---|---|
| 1 | 拍摄标准 | 素材不合格 → 算法在垃圾输入上做精细计算 |
| 2 | 标注质量 | 无真值 → 不知道算法做到什么程度算好 |
| 3 | 指标算法 | 数字错 → 结论错，且看起来合理 |
| 4 | 规则与标准值 | 判断错 → 教练失去信任 |
| 5 | 界面与产品 | 前四步错了，界面做得再漂亮也没意义 |

### 1.1 最常见的时间浪费

单人项目最大的浪费不是"做得慢"，而是**顺序错了导致返工**：

| 错误顺序 | 代价 |
|---|---|
| 先写界面，后定契约 | 契约确定后界面全部重写 |
| 先做模型，后验拍摄 | 模型在不可用的素材上优化，精度指标无意义 |
| 先写规则，后采标准值 | 阈值凭印象填，结论系统性错误 |
| 先做产品，后验需求 | 做完了发现教练不用 |

## 2. 四条并行轨

阶段是串行的，但**同一阶段内部有多条轨可以并行**。

```
时间轴 →

规范轨   规范冻结 ──────────────────────────────────────►
                        │
数据轨                  └─ 拍摄规范落地 ─ 素材采集 ─ 标注 ─ QC ─ 金标准 ──►
                        │
工具轨                  ├─ 环境搭建 ─ 帧率校验 ─ 镜头运动检测 ─ 视角校验
                        │              ─ 参考尺度 ─ 姿态提取 ─ 指标计算 ──►
                        │
产品轨                  └────── 契约冻结后才开始 ──────────────────►
                                                          ↑
                                                     App / 报告
                        │
验证轨                  └──── 链路打通后立即商业验证 ──────────►
```

**关键约束：产品轨必须等契约冻结才能开始。**

这不是保守，而是"契约与实现解耦"原则的直接要求。契约未定时写界面，契约一改就要重写。

## 3. 关键路径

```
① 规范冻结（本文档集）
        ↓
② 帧率校验 + 镜头运动检测 + 视角校验     ← ★ 最长单项
        ↓
③ 素材采集（≥20 段，多运动员、三视角）
        ↓
④ 人工标注 + 四道 QC                     ← ★ 含 7 天强制等待期
        ↓
⑤ 姿态提取 + 指标实现（对照金标准）
        ↓
⑥ 规则库 + 标准值库
        ↓
⑦ 报告 → 产品化
```

### 3.1 三个瓶颈

| 瓶颈 | 位置 | 为什么是瓶颈 |
|---|---|---|
| **帧率校验 + 镜头运动检测** | 最早 | 结论决定哪些指标存在。不确定它们，指标清单就冻结不了 |
| **QC-1 的 7 天等待** | 标注阶段 | **不可压缩**。记忆效应会使 7 天内重标失去意义 |
| **教练复核 ≥20 份报告** | 规则阶段 | 依赖教练时间，不在你控制内，需提前预约 |

### 3.2 时间占比（相对值）

| 工作 | 占比 | 说明 |
|---|---|---|
| 环境与工具搭建 | 10% | 一次性 |
| 素材采集 | 15% | 含三视角、多运动员 |
| **标注 + QC** | **25%** | **最容易低估。含 7 天等待** |
| 指标实现与验证 | 20% | 20 个指标，每个需手工验算 |
| 规则与标准值 | 20% | 文献检索耗时不可控 |
| 产品化 | 10% | 契约冻结后进展最快 |

> **最容易低估的是"标注 + QC"。** 它看似简单，但含强制等待期、需要重复标注、需要逐帧目视叠加图。实际耗时通常是预估的 2 倍。

## 4. 七个不可逆点

**有些决定一旦做了，改的代价极高。**

| 不可逆点 | 改的代价 | 必须在何时确认 |
|---|---|---|
| **关键点集合（16 点）** | 全部标注数据作废 | 标注第一帧之前 |
| **事件定义（8 类）** | 同上 | 同上 |
| **契约字段** | 客户端全部重写 | 写业务代码前 |
| **指标公式** | 历史数据全部重算 | 指标实现后不可改 |
| **多租户设计** | 数据层全部重写 | 建第一张表时 |
| **拍摄标准** | 已采集数据需重新评估 | 第一次采集前 |
| **视角定义与绑定规则** | 全部指标与规则需重审 | 指标实现前 |

### 4.1 三个最容易踩的

**第一，关键点集合。**

标注是最贵的工作（占 25%）。标了 200 帧才发现需要补一个关键点，这 200 帧要重标。

**本项目已定为 16 点**，含足部（`heel` / `toe`）与骨盆/肩中心。**不追加肘、腕。**

**第二，帧率校验与镜头运动处理的结论。**

如果先用容器帧率跑完全部指标，之后才发现帧率错了，那所有时间类指标都要在错误基础上重算，且**你无法知道哪些结论是错的**——因为它们看起来都正常。

**第三，多租户。**

单人项目容易想"先做单队，以后再改多队"。但多租户改造涉及所有表结构、所有查询、所有存储路径。

**要求：建第一张表时就带上 `team_id`。**

## 5. 单周工作循环

```
周一            确定本周 1–3 项任务（不超过 3 项）
                ↓
周二 — 周四      执行
                ↓
周五上午         跑全部门禁 + 更新进度记录
                ↓
周五下午         ★ 验证：本周产出是否回答了一个未验证假设？
                ↓
                有 → 记录结论，更新 00-项目介绍 §7 假设状态
                无 → 下周优先安排一项验证工作
```

### 5.1 为什么周五下午的验证必须固定

`00-项目介绍.md` §7 列了 6 条关键假设（A1–A6），全部"待验证"。**假设不会自己变成事实。**

如果连续两周没有任何假设被验证，说明在做闭门造车——这是最危险的信号。

### 5.2 每周任务上限 3 项

单人项目同时推进 5 项，结果是 5 项都没完成。

## 7. 并行关系总表

> 这张表回答"我现在能不能同时做另一件事"。

| 工作 | 可与之并行 | 不可与之并行 |
|---|---|---|
| 帧率校验 | 畸变校正、姿态提取调研 | 指标计算（依赖其结论） |
| 镜头运动检测 | 视角校验、参考尺度 | 指标实现 |
| 素材采集 | 工具链开发 | 无 |
| 人工标注 | 工具链开发、标准值检索 | 无 |
| **QC-1 的 7 天等待** | **指标实现、标准值检索** | 无 |
| 指标实现 | 标准值检索、处方收集 | 规则编写（依赖标准值） |
| 标准值检索 | **任何阶段** | 无 |
| 报告渲染 | App 界面开发 | 无 |
| 界面开发 | Web 端、App 端互可并行 | 契约冻结前不可开始 |
| 规则编写 | 处方收集 | 教练复核（依赖规则） |

### 7.1 可以立刻开始、且任何阶段都不冲突的两件事

| 工作 | 原因 |
|---|---|
| **标准值文献检索** | 纯查文献，不依赖代码，是规则库的前置条件 |
| **向教练收集训练手段** | 为处方库积累素材，不依赖任何技术产出 |

**共同特点：不占开发时间，只占日历时间，越早开始越好。**

## 8. 常见误区

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| 先做界面，契约后定 | 契约一改界面全废 | 契约冻结后才开产品轨 |
| 先做模型，后验拍摄 | 素材不合格时模型精度无意义 | 帧率校验与拍摄标准优先 |
| 先写规则，后采标准值 | 阈值凭印象填，结论系统性错误 | 标准值先行，或至少并行 |
| 自己编处方 | 教练不认，不会用 | 向教练收集 |
| 等标注全做完再写指标 | 金标准可分批产出 | 用已标注部分先验证 |
| **忽略镜头跟踪的影响** | 数据看起来正常但位移类全错 | 按指标类别分级处理 |
| **把三种视角混在一起** | 矢状面与额状面混淆 | 视角绑定指标，严格分流 |
| 跳过 QC-4 目视 | 脚本判断不了"点是否在正确关节" | 逐帧目视，不可替代 |
| 压缩 QC-1 的 7 天 | 记忆效应使重标失效 | 期间并行做指标实现 |
| 质量门等到后期再补 | 文档与代码已脱节 | P1 就建立 |
| 单队先做，多队后改 | 数据层全部重写 | 建第一张表就带 `team_id` |

## 9. 进度自检

**每周五回答下列问题：**

- [ ] 本周完成的 1–3 项工作，属于关键路径吗？
- [ ] 有没有做"现在做等于白做"的事？
- [ ] 本周是否验证了一条假设？（连续 2 周"否"即为危险信号）
- [ ] 质量门是否仍然全部通过？
- [ ] 文档与代码是否仍然一致？

**每个阶段结束回答：**

- [ ] 本阶段的出口标准全部满足？
- [ ] 上游是否有未验证的假设被带下来了？
- [ ] 下一阶段的前置条件是否已就绪？
- [ ] 是否触碰了任何不可逆点？
