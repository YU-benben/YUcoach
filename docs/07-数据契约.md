## 1. 版本策略

### 1.1 变更类型与版本

| 变更类型 | 版本递增 | 客户端处理 |
|---|---|---|
| 删除字段 | **Major** | 旧客户端必须拒绝，提示升级 |
| 修改字段含义 | **Major** | 同上 |
| 修改字段类型 | **Major** | 同上 |
| 新增**必填**字段 | **Major** | 同上 |
| 新增**可选**字段 | Minor | 旧客户端忽略 |
| 新增枚举值 | Minor | 旧客户端需有 default 分支 |
| 修正文档、注释 | Patch | 无影响 |

### 1.2 兼容性铁律

> **客户端必须忽略未知字段，不得因出现新字段而报错。**

### 1.3 契约校验（必须实现为代码）

**文档描述的契约会很快与代码脱节，这是所有规范类文档最常见的死法。**

要求：
1. 本文件的每个 Schema 必须有对应的 JSON Schema 文件，存放于 `backend/contracts/`
2. 每次提交必须运行契约校验，比对实际响应与 Schema
3. 每次提交必须与上一版本 Schema 做兼容性比对

## 2. 通用约定

### 2.1 响应包裹

```json
{ "code": 0, "message": "ok", "data": { } }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | `0` 表示成功 |
| `message` | string | 人类可读，**不得用于程序判断** |
| `data` | object / null | 成功时的负载 |

### 2.2 错误码分段

| 段 | 含义 | 示例 |
|---|---|---|
| 1xxx | 认证与权限 | `1001` 未登录；`1003` 无该队伍权限 |
| 2xxx | 参数错误 | `2001` 缺必填参数；`2002` 枚举值非法；`2003` 分页越界 |
| 3xxx | 资源状态 | `3001` 场次不存在；`3002` 分析未完成 |
| 4xxx | **业务拒绝** | `4001` 素材质量不合格；`4002` 帧率校验未通过；`4003` 视角无法确认 |
| 5xxx | 服务异常 | `5001` 模型推理失败；`5002` 存储不可用 |

**4xxx 是可选返回**：业务拒绝但可继续时，优先返回**部分成功**并在 `data` 中标记数据不足，而非直接报错。

### 2.3 时间与坐标

| 项 | 约定 |
|---|---|
| 时间基准 | **帧号** |
| 毫秒值 | 由 `帧号 / fps_verified × 1000` 导出 |
| 时间零点 | 由 `time_base` 声明，默认 `gun_fire` |
| 坐标 | 归一化（0–1），原点在画面左上角，y 轴向下 |
| 坐标系统识 | 由 `coord_system` 字段声明 |

### 5.2 字段语义

| 字段 | 类型 | 说明 |
|---|---|---|
| `view.declared` / `view.detected` / `view.agreement` | — | 视角校验三元组 |
| `time_base.origin_frame_index` | int | 时间零点的帧号 |
| `frames[].keypoints` | array | **定长数组**，长度恒等于 `keypoint_names` 长度 |
| `keypoints[].q` | int | `0` 不可见 / `1` 存疑 / `2` 清晰 |
| `frames[].measurement_window` | enum | **`valid` / `degraded` / `excluded`** |
| `frames[].skew_deg` | float | 该帧的视线偏斜角估计 |
| `frames[].pixels_per_meter` | float \| null | **该帧的参考尺度**（跟踪拍摄下逐帧不同） |
| `is_interpolated` | bool | 该帧为插值补出，非实测 |

### 5.3 四条强制规则

**规则一：`keypoints` 必须是定长数组。**

即使某点不可见，也必须占位（`q: 0`），便于客户端按下标取值。

**规则二：`q = 0` 与"点不存在"含义不同。**

| 表达 | 含义 | 客户端行为 |
|---|---|---|
| `{ "x": 0, "y": 0, "q": 0 }` | 该点不可见或未标注 | 不绘制 |
| 数组中缺少该下标 | 数据结构异常 | 报错 |

**规则三：`is_interpolated: true` 必须显式标注。**

插值补出的点是**猜的**。标记后客户端应画成虚线，不能与实测混淆。

**规则四：`pixels_per_meter` 是逐帧字段，不是全局字段。** ⚠️

跟踪拍摄下距离逐帧变化，**不存在全局的像素↔米比例**。

| 字段 | 用途 |
|---|---|
| `source.reference_scale.median_pixels_per_meter` | 中位值，用于报告概览 |
| `frames[].pixels_per_meter` | **逐帧实际值，用于计算** |

**客户端与后端在做任何位移换算时，必须使用逐帧值。**

### 5.4 帧窗口拉取（必须实现）

整段姿态数据体积可达数 MB（2400 帧 × 16 点 × 3 字段 ≈ 115,200 个数值），一次性返回会导致手机端卡死。

```
GET /api/v1/analyses/{id}/pose?from=940&to=990
```

| 限制 | 值 |
|---|---|
| 单次最大返回帧数 | 600 |
| 超出时 | `code: 2003`，`message` 给出建议区间 |

**实践中客户端只需拉取事件帧附近几十帧用于叠加回放。**

### 6.2 字段要求

| 字段 | 必填 | 说明 |
|---|---|---|
| `metric_id` | ✅ | 见 `03-指标定义.md` |
| `view` | ✅ | **该指标所属视角** |
| `phase` | ✅ | 该值所属阶段 |
| `value` | ✅ | 单帧/单次值。`insufficient_data` 时为 `null` |
| `aggregate` | ✅ | **同阶段多步次的统计量**。`n` 必须给出 |
| `valid_frame_count` / `total_frame_count` | ✅ | **有效帧占比**，反映跟踪拍摄的影响 |
| `ref.applicable_phase` | ✅ | **与 `phase` 不符时 `deviation` 必须为 `null`** |
| `ref.view` | ✅ | **与 `view` 不匹配时该 ref 不可用** |
| `ref.source` | ✅ | `literature` / `team` / `global` |
| `deviation` | ✅ | 标准化偏离，可为 `null` |
| `confidence` | ✅ | 0–1 |
| `reliability` | ✅ | `A` / `B` / `C` |
| `reliable` | ✅ | 布尔 |
| `perspective_error_estimate` | ✅ | **该指标的透视误差量级** |
| `insufficient` | ✅ | 数据不足时的详细说明，否则 `null` |

### 6.3 `confidence` 与 `reliable` 的区别（不可合并）

| 字段 | 回答的问题 | 类型 |
|---|---|---|
| `confidence` | 这个数**准不准** | 连续 0–1 |
| `reliable` | 这个数**该不该用** | 布尔 |

**可以既 confident 又 unreliable**：角度本身测得很稳（`confidence` 0.9），但运动员全程处于画面边缘（`reliable: false`，因为系统性透视偏差无法通过重复测量发现）。

### 6.4 展示规则

> **`reliable: false` 的指标必须显示但标注警示，不得隐藏。**
>
> 隐藏会让教练怀疑数据被挑选过。

### 7.2 字段要求

| 字段 | 必填 | 说明 |
|---|---|---|
| `rule_id` | ✅ | **结论的责任人。** 教练质疑时据此追溯 |
| `rule_version` | ✅ | 规则版本 |
| `severity` | ✅ | `major` / `minor` / `info` / `insufficient_data` |
| `view` / `phase` | ✅ | 该结论的适用条件 |
| `title` | ✅ | ≤ 20 字 |
| `metric_ids` | ✅ | 关联指标，供界面联动 |
| `evidence` | ✅ | 实测值、标准区间、偏离量 |
| `explanation` | ✅ | **必须写机制，不得重复现象** |
| `confidence` | ✅ | 结论置信度 |
| `basis` | ✅ | `normal` / `low_reliability` / `single_sample` / `extrapolated` |
| `caveat` | ✅ | 低置信度时的提示 |
| `drills` | ✅ | **不超过 3 个** |

### 7.3 三条强制规则

**规则一：`rule_id` 必填。**

> 教练问"凭什么这么说"，要能回答"这是规则库第 N 条规则，触发条件是躯干角低于阶段下限"。
>
> 没有这条链，系统就是黑箱。

**规则二：`explanation` 必须写机制。**

| 写法 | 评价 |
|---|---|
| "躯干角偏小。" | ❌ 重复 `title` |
| "躯干角偏小，说明身体过早抬起，会缩短水平推进的有效做功距离。" | ✅ 后半句是教练需要的 |

**规则三：`confidence` 必须传导上游不确定性。**

若依据的指标 `reliable: false`，结论 `confidence` 必须 ≤ 0.5，`basis` 必须为 `low_reliability`。

### 7.4 数据不足型结论

```json
{
  "finding_id": "f_0012",
  "severity": "insufficient_data",
  "view": "front",
  "phase": "max_velocity",
  "title": "骨盆控制无法评估",
  "reason": "view_mismatch",
  "required": "正面或背面视角",
  "actual": "侧面视角",
  "impact": ["pelvis_tilt", "pelvis_drop_midstance"],
  "suggestion": "补拍一段正面或背面视角的视频，即可评估骨盆控制与左右对称性",
  "rule_id": null,
  "metric_ids": [],
  "confidence": null,
  "drills": []
}
```

**数据不足是明确的状态，不是沉默。**

### 10.1 视频上传要求

| 项 | 要求 |
|---|---|
| 分片大小 | 5–10 MB |
| 断点续传 | 记录已完成分片 |
| **转码** | **禁止**。必须上传原始文件 |
| **压缩** | **禁止**。`Content-Encoding: identity` |
| 后台继续 | 前台服务 + 通知 |

> **上传的必须是原始文件，一字节不得转码。**
>
> 转码会重写帧率、丢弃或插值帧、降低码率，全部破坏分析依据。

### 10.2 人工修正接口

```
POST /api/v1/corrections
```

```json
{
  "session_id": "s_20260301_at00007_01",
  "analysis_id": "a_s_20260301_at00007_01_v2",
  "target": "keyframe",
  "frame_index": 955,
  "payload": {
    "original_event": "midstance",
    "corrected_frame": 953,
    "reason": "重心最低点在 953 帧"
  }
}
```

| `target` | 说明 |
|---|---|
| `keypoint` | 修正关节点位置 |
| `keyframe` | 修正事件帧号 |
| `phase` | 修正阶段切分 |
| `view` | 修正视角声明 |
| `reference_scale` | 提供参考尺度 |

**修正数据必须入库且不可删除。** 教练的每一次修正，都是免费的标注。
