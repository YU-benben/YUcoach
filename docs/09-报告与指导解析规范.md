# 09 · 报告与指导解析规范

| 项 | 值 |
|---|---|
| 文档版本 | 2.0.0 |
| 状态 | 已冻结 |
| 作用 | 定义报告的固定结构、措辞规则、指导解析的生成方式 |
| 核心要求 | **报告是产品的最终交付物。其他所有模块都是为它服务的。** |

---

## 1. 报告存在的目的

> **报告不是数据的展示，是一份行动建议。**

判断报告好坏的标准只有一个：**教练看完之后，是否知道下次训练该做什么。**

不是"信息是否完整"，不是"图表是否精美"，不是"数据是否详尽"。

### 1.1 三条硬规则

| # | 规则 | 理由 |
|---|---|---|
| 1 | 建议条目 ≤ 3 条 | 给 10 条问题等于没给，教练一条都不会改 |
| 2 | 每条建议必须含机制解释 | 教练知道为什么是问题，才会去改 |
| 3 | 数据不足必须明说 | 沉默会被误读为"没问题" |

---

## 2. 报告结构（固定，顺序不可改）

| # | 区块 | 内容 | 约束 |
|---|---|---|---|
| 1 | 头部 | 运动员、日期、**视角**、测试类型、**拍摄质量分**、**分析口径** | 必含视角与质量分 |
| 2 | 总览 | 一句话总结 + 改进项数量 | ≤ 60 字 |
| 3 | 关键帧图解 | 原图 + 骨架 + 角度弧线 + **尺度条** | 每个 major 结论至少 1 张 |
| 4 | 指标对比 | 横向条形图，**按视角分组** | 只显示可判定指标 |
| 5 | 指导解析 | ≤3 条，每条：标题 + 实测 + 机制 + 处方 | 顺序固定 |
| 6 | 附录 | 置信度说明、拍摄质量、帧率校验、视角说明、局限性 | 必含免责 |

**顺序不可调整。** 教练的阅读路径是从上到下，需要先看结论再看支撑。

---

## 3. 各区块详细规范

### 3.1 头部

```
┌────────────────────────────────────────────────┐
│  张三 · 100m · 加速段技术                        │
│  2026-03-01                    [侧面视角]        │
│                           拍摄质量 78 分 ⓘ      │
│  分析口径 2026.03.1                             │
└────────────────────────────────────────────────┘
```

| 元素 | 要求 |
|---|---|
| 运动员 | 姓名 + 项目 + 测试类型 |
| 日期 | 采集日期（非报告生成日期） |
| **视角标签** | **必须显示**。它决定了这份报告能说什么 |
| 拍摄质量分 | **必须显示**。点击展开明细 |
| 分析口径 | 复合版本标识 |

**为什么必须显示视角**：教练需要知道这份报告**没有**评估什么。侧面视角的报告不谈骨盆控制，这不是遗漏，是方法边界。

### 3.2 总览

```
┌────────────────────────────────────────────────┐
│  加速段躯干前倾不足，其余指标在合理范围           │
│                                                │
│  发现 1 处可改进 · 2 项数据不足                  │
└────────────────────────────────────────────────┘
```

| 字段 | 来源 | 约束 |
|---|---|---|
| 一句话总结 | 服务端**确定性生成** | ≤ 60 字 |
| 改进项数量 | `major_count + minor_count` | — |
| 数据不足数量 | `insufficient_count` | 有则必须显示 |

**"一句话总结"的生成规则**（不由 LLM 自由撰写）：

```
若 major ≥ 1：  "<主要问题标题>，其余指标<总体评价>"
若 仅 minor：   "未发现显著问题，<minor 问题>有改进空间"
若 仅 info：    "各项指标均在合理范围"
若 全部不足：   "本次数据不足以完成评估，建议重新采集"
```

### 3.3 关键帧图解

```
┌────────────────────────────────────────────────┐
│  着地 (touchdown) · 第 2 步 · 加速段             │
│  ┌──────────────────────────────────────────┐  │
│  │                                          │  │
│  │      [原图 + 骨架叠加 + 角度弧线]          │  │
│  │                                          │  │
│  │   胫骨角 12.4°   膝角 158.2°              │  │
│  │   [标准 8–15°] ✓                         │  │
│  └──────────────────────────────────────────┘  │
│  ├────┤ 0.5 m                        侧面视角   │
└────────────────────────────────────────────────┘
```

| 元素 | 要求 |
|---|---|
| 骨架叠加 | 侧面：近侧实线黄 / 远侧虚线灰；正背面：左右不同色 |
| 角度弧线 | 在对应关节绘制，标注角度值与标准区间 |
| **尺度条** | **必须绘制**，见下方说明 |
| 事件标签 | 事件中文名 + 英文 ID + 步次 + 阶段 |
| 视角标签 | 标明本图的视角 |
| 低置信标注 | 该帧若为插值，左上角显示"推算帧"标记 |

#### 尺度条的必要性 ⚠️

> **跟踪拍摄下，同一段视频中不同帧的运动员像素尺寸不同。**
>
> 如果不标注尺度，教练对比两张关键帧图时会误以为"这个人变大了/变小了"。

**每张关键帧图必须画一条比例尺**，标注该帧的像素↔米比例（对应契约中的 `keyframes[].pixels_per_meter`）。

### 3.4 指标对比（按视角分组）

```
── 侧面视角（矢状面）──────────────────────────
着地胫骨角        12.4°   ├────▓────┤   标准 8–15°    ✓
着地膝角         158.2°   ├──▓──────┤   标准 150–178° ✓
支撑中期膝角     142.0°   ├─────▓───┤   标准 130–155° ✓
躯干前倾角        38.2°   ├▓────────┤   标准 45–60°   ⚠
触地时间         183 ms?  ├──▓──────┤   标准 160–220  ⚠
步幅                ——    ┌──────────────────────────┐
                          │ 数据不足：缺少参考尺度     │
                          │ 需要 ≥2 条分道线入画       │
                          └──────────────────────────┘

── 正面/背面视角（额状面）──────────────────────
着地膝内扣角        ——    ┌──────────────────────────┐
                          │ 需要正面或背面视角         │
                          │ 当前为侧面视角             │
                          │ 建议：补拍一段正面视角      │
                          └──────────────────────────┘
骨盆倾斜角          ——    同上
```

| 元素 | 要求 |
|---|---|
| 视角分组 | **必须分组并标明**，不可混在一起 |
| 标准区间 | 浅蓝底色条 |
| 本人数值 | 圆点标记 |
| 判定符号 | `✓` / `⚠` / `?` |
| 低置信指标 | 数值后加 `?`，下方一行说明原因 |
| 数据不足指标 | 灰色占位块 + 原因 + 改进建议 |

**不显示标准化偏离值。** 界面只回答"在不在区间内"。

### 3.5 指导解析（报告核心区块）

```
┌─────────────────────────────────────────────────┐
│ ● 加速段躯干过早直立                              │
│                                                 │
│   实测 38.2°                                     │
│   该阶段应有 45–60°（低于下限 6.8°）              │
│                                                 │
│   加速段躯干前倾角不足，说明身体过早抬起，         │
│   会缩短水平推进的有效做功距离。                  │
│                                                 │
│   建议练习                                       │
│   ┌───────────────────────────────────────────┐ │
│   │ 推墙加速跑                                 │ │
│   │ 4 组 × 8 次 · 组间 90 秒                   │ │
│   │ 口令：保持躯干前倾，让身体呈一条斜线         │ │
│   └───────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

**固定结构（顺序不可变）：**

| 序 | 元素 | 来源 |
|---|---|---|
| 1 | 标题 | `finding.title` |
| 2 | 实测值与标准区间 | `finding.evidence` |
| 3 | 机制解释 | `finding.explanation` |
| 4 | 处方 | `finding.drills` |

**处方块的必含元素**：动作名 + 组次 + **口令**。

> **口令是处方块中最重要的一行。**
>
> 教练在跑道边只有 3 秒把要点传达给运动员，他只会喊一句口令，不会念动作要领。

### 3.6 附录

| 部分 | 内容 |
|---|---|
| 置信度说明 | 哪些指标低置信、原因是什么 |
| 拍摄质量报告 | 各分项得分与扣分原因 |
| 帧率校验结果 | 声明值 / 校验值 / 方法 / 一致性 |
| **镜头跟踪说明** | 是否检测到镜头移动、有效帧占比 |
| **视角说明** | 本报告覆盖哪些指标、未覆盖哪些及原因 |
| 局限性声明 | 固定文本，见 §5 |

## 4. 指导解析的生成方式

### 4.1 职责分离（关键设计）

```
计算层（确定性）      →  指标数值
      ↓
规则引擎（确定性）    →  偏差项 + 严重度 + 关联缺陷 + 候选处方
      ↓
文案层（模板 + LLM）  →  把结构化结论翻译成教练能读懂的话
```

> **大模型不得参与数值计算，也不得凭空生成结论。**
>
> 它只能对规则引擎已经确定的结构化结论做语言组织。这是保证报告可信的底线。

### 4.2 文案层的输入输出

| 输入（来自规则引擎） | 输出（写入报告） |
|---|---|
| `title` | 直接使用 |
| `evidence` | 格式化为"实测 X，应有 Y" |
| `explanation` | 机制解释段落 |
| `drills[].cue` | 口令行 |
| `confidence` / `basis` | 是否附加强调或免责 |

**LLM 唯一可自由发挥的地方是 `explanation` 的措辞润色**，且必须：

- 保留原有的机制表述
- 不得引入新的数字
- 不得引入因果断言（"一定是因为…"）

### 4.3 确定性生成的部分

以下内容**必须由模板生成，不得由 LLM 生成**：

| 内容 | 原因 |
|---|---|
| 一句话总结 | 必须与结论数量、严重度严格一致 |
| 实测值与标准区间 | 数字错误后果严重 |
| 数据不足的说明 | 必须准确对应 `reason` |
| 处方组次与口令 | 教练据此执行，不容改写 |
| 免责声明 | 固定文本 |

## 5. 措辞规范

### 5.1 必须区分"测量"与"推断"

| 场合 | 措辞 | 禁止 |
|---|---|---|
| 直接测量值 | "着地胫骨角为 12.4°" | 不得说"大约是" |
| 统计推断 | "高于本队同水平运动员均值" | 不得说"明显偏高" |
| 文献对比 | "超出该类动作的常见范围（参考值 8–15°）" | 不得说"错误的" |
| 模型预测 | **不使用** | 本系统不做预测 |

### 5.2 禁止措辞

| 禁止 | 原因 | 替代 |
|---|---|---|
| "你的跑姿很差" | 评价人，不评价动作 | "着地点偏前" |
| "严重错误" | 无信息量且打击性 | "低于该阶段应有范围" |
| "一定是…导致的" | 二维视频无法确立因果 | "说明…，会…" |
| "建议加强核心力量" | 无指向，教练无法执行 | 具体动作 + 组次 + 口令 |
| 任何未标注来源的具体数字 | 违反数据可信原则 | 标注 `ref.source` |
| "正常情况下应该…" | 模糊 | 给出具体区间与来源 |

### 5.3 措辞与 `ref.source` 的对应

| `ref.source` | 措辞模板 |
|---|---|
| `literature` | "超出常见范围（参考值 X–Y，来源：文献）" |
| `team` | "高于/低于本队同水平运动员均值（本队均值 X）" |
| `global` | "高于/低于同项目运动员均值（平台均值 X）" |

**队内对比的措辞说服力最强**，因为教练信任自己的数据。

### 5.4 数据不足的措辞（三要素）

**必须包含：是什么、为什么、怎么办**

```
步幅无法评估
原因：画面中未见跑道分道线，且未填写运动员身高，
      无法进行像素到实际距离的换算。
建议：拍摄时让跑道分道线入画，或在运动员档案中补充身高。
      其余指标不受影响。
```

| 要素 | 缺失的后果 |
|---|---|
| 是什么 | 教练不知道有这项指标 |
| 为什么 | 教练以为是系统故障 |
| 怎么办 | 下次采集仍然拍错 |

### 5.5 视角不匹配的措辞

```
骨盆倾斜角无法评估
原因：该指标需要从运动员正前方或正后方拍摄，本次为侧面视角。
说明：侧面视角只能评估关节角度与躯干前倾，无法评估骨盆控制与左右对称性。
建议：如需评估骨盆控制，请补拍一段正面或背面视角的视频。
```

> **必须让教练明白这不是系统缺陷，而是方法边界。** 同时告诉他补拍能获得什么。

## 6. 免责声明分级

### 6.1 按拍摄质量分分级

| 质量分 | 声明强度 | 呈现方式 |
|---|---|---|
| ≥ 75 | 标准说明 | 附录中描述方法学局限 |
| 55–74 | 部分受限 | **报告顶部横幅**："本报告部分指标精度受限" |
| < 55 | 仅供参考 | **报告顶部横幅**："本报告结论仅供参考，不建议用于训练决策" |

### 6.2 固定声明文本

**所有报告必须包含**（置于附录末尾）：

> 本报告基于二维视频分析，用于技术动作的观察与趋势对比。
>
> 不构成医学诊断，不替代教练的专业判断，不可用于反推地面反作用力或关节负荷。
>
> 可靠性等级为 C 的指标仅适用于趋势对比，不应单独作为训练依据。
>
> 由于拍摄时镜头跟随运动员移动，运动员偏离画面中心较远时，测量存在透视误差，
> 本报告已在相应位置标注误差量级。

### 6.3 附加声明的触发条件

| 条件 | 附加声明 |
|---|---|
| 存在 `reliable: false` 指标 | "本报告含 N 项精度受限指标，已在相应位置标注" |
| 存在 `insufficient_data` | "本报告有 N 项指标因数据不足未能评估" |
| `fps_verify.status == warning` | "帧率校验存在不确定性，时间类指标精度受限" |
| 无参考尺度 | "本次未获得参考尺度，位移类指标不可用" |
| `camera_motion.level == strong_pan` | "检测到镜头明显跟随移动，部分角度指标存在透视误差" |
| 有效帧占比 < 50% | "运动员较长时间处于画面边缘，建议下次拍摄让运动员更多处于画面中心" |
| 视角为侧面 | "本报告未评估骨盆控制与左右对称性，需正面或背面视角" |
| 视角为正/背面 | "本报告未评估关节角度与躯干前倾，需侧面视角" |

## 7. 格式形态

### 7.1 交互式报告（App / Web）

| 特性 | 说明 |
|---|---|
| 可交互 | 点击指标查看定义与来源；点击关键帧放大 |
| 可筛选 | 按视角筛选指标 |
| 可跳转 | 从结论跳到对应关键帧 |
| 实时更新 | 重新分析后即时刷新 |

### 7.2 PDF 报告（导出 / 存档 / 打印）

| 特性 | 说明 |
|---|---|
| 固定布局 | A4 纵向，页边距 20 mm |
| 完整自包含 | 不依赖网络，图片内嵌 |
| 页数控制 | 2–4 页 |
| 页码与生成时间 | 页脚 |

**PDF 不是交互式报告的截图**，而是独立排版。理由：PDF 用于打印和存档，需保证在小屏和大屏上都能读清。

### 7.3 内容一致性

**两份形态的内容必须完全一致。** 不得出现"PDF 里没有某条建议"的情况——否则教练之间传阅时会产生信息差。

## 8. 报告质量检查清单

**每份报告生成后自动检查：**

- [ ] 头部包含视角标签
- [ ] 头部包含拍摄质量分
- [ ] 头部包含分析口径
- [ ] 总览 ≤ 60 字
- [ ] 指导解析 ≤ 3 条
- [ ] 每条解析包含：标题、实测值、标准区间、机制解释、处方
- [ ] 每个 major 结论有对应关键帧图
- [ ] 每张关键帧图有**尺度条**
- [ ] 每条处方的口令已显示
- [ ] 指标按视角分组
- [ ] 所有 `reliable: false` 指标有显式警示
- [ ] 所有 `insufficient_data` 指标有原因与改进建议
- [ ] 附录包含固定免责声明
- [ ] 附录包含帧率校验结果
- [ ] 附录包含镜头跟踪说明
- [ ] 附录包含视角说明
- [ ] 无技术术语（`z-score`、`JSON`、`null`）
- [ ] 无未标注来源的具体数字
- [ ] 无评价性措辞（"很差"、"严重错误"）

**任一项不通过，报告不得发布。**

## 9. 报告的迭代依据

报告结构不是一次定稿的。迭代依据按优先级：

| 依据 | 收集方式 |
|---|---|
| 教练能否在 60 秒内说出"该改什么" | 观察 + 访谈 |
| 教练是否执行了建议 | 4 周后回访 |
| 哪一块被跳过不读 | 交互式报告的滚动与点击埋点 |
| 哪一条被质疑 | 教练反馈记录 |
| **哪一项"数据不足"出现最多** | 统计 `insufficient.reason` 分布 |

> **最有价值的迭代信号有两个：**
>
> 1. **教练跳过了哪一块** —— 被跳过的区块，要么信息冗余，要么位置错误，要么根本不重要
> 2. **哪种"数据不足"最常见** —— 它直接告诉你教练的拍摄习惯有什么系统性问题，是改进拍摄引导的依据
