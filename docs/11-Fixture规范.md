# 11 · Fixture 规范（无后端开发）

| 项 | 值 |
|---|---|
| 文档版本 | 1.0.0 |
| 状态 | 已冻结 |
| 适用场景 | 后端未就绪时，App 的独立开发与测试 |
| 核心目标 | **接后端时只切换数据源，不改一行业务代码** |

---

## 1. 为什么需要这份文档

`08-App功能与交互规范.md` 定义了界面长什么样，但没有回答一个实际开发问题：

> **后端还没做完，App 用什么数据开发？**

如果不解决这个问题，会出现三种情况：

| 情况 | 后果 |
|---|---|
| 数据写死在 widget 里 | 接后端时全部重写 |
| 用随机数生成 | 每次运行结果不同，无法写快照测试；数值语义错误但界面不报错 |
| 等后端做完 | App 开发被阻塞 |

**本规范的目的：让 App 可以在零后端的情况下完成 90% 的开发，并且接后端时零返工。**

---

## 2. 核心设计：可切换的数据源

```
┌─────────────────────────────────────┐
│  UI 层（报告页 / 指标卡 / 骨架叠加）    │
│  —— 只认领域模型，不认数据来源          │
└──────────────┬──────────────────────┘
               │ 依赖抽象，不依赖实现
┌──────────────▼──────────────────────┐
│  AnalysisRepository（抽象接口）        │
│  getAnalysis(id)                      │
│  getPose(id, from, to)                │
│  getKeyframe(analysisId, frameIndex)  │
│  getTask(taskId)                      │
└──────────────┬──────────────────────┘
               │
     ┌─────────┼─────────┐
     ▼         ▼         ▼
 Fixture   Recorded    Http
 （开发）   （回归）    （生产）
```

### 2.1 三种实现

| 实现 | 数据来源 | 用途 |
|---|---|---|
| `FixtureDataSource` | `assets/fixtures/*.json` | 日常开发、UI 调试、截图 |
| `RecordedDataSource` | 抓取的真实后端响应（存为文件） | **回归测试**：防止 UI 因真实数据变化而崩 |
| `HttpDataSource` | 真实 API | 生产 |

**`RecordedDataSource` 是最容易被忽略但最有用的一层。** 真实后端的响应往往有 fixture 里没有的边界情况（超长字符串、null 字段、极端数值）。把真实响应录下来做测试，能在没连后端时就发现这些。

### 2.2 切换方式

```dart
final analysisRepositoryProvider = Provider<AnalysisRepository>((ref) {
  const env = String.fromEnvironment('ENV', defaultValue: 'fixture');
  switch (env) {
    case 'fixture':  return FixtureDataSource();
    case 'recorded': return RecordedDataSource();
    case 'http':     return HttpDataSource(baseUrl: apiBaseUrl);
    default:         throw StateError('unknown ENV: $env');
  }
});
```

启动时切换，**不改一行业务代码**：

```bash
flutter run --dart-define=ENV=fixture
flutter run --dart-define=ENV=http --dart-define=API_BASE=https://...
```

### 2.3 模型必须由 Schema 生成

```
backend/contracts/*.schema.json  →  scripts/gen_models.py  →  mobile/lib/models/*.dart
```

**不得手写客户端模型。**

理由：手写模型与契约的漂移是必然的。契约改了字段名，前端不会报错，只会静默收到 `null`，然后在某个界面上显示成空白——而且可能在两周后才被发现。

## 3. Fixture 清单

> **每一份 fixture 都必须严格符合 `07-数据契约.md` 的 Schema。一个字段都不能凑合。**

### 3.1 必需 fixture（6 份）

| 文件 | 内容 | 覆盖场景 | 状态 |
|---|---|---|---|
| `analysis_normal.json` | 全部指标正常，有 2 条结论 | 主路径 | ✅ 已提供 |
| `analysis_low_confidence.json` | 含 `reliable: false` 指标与 caveat 结论 | 低置信展示 | ✅ 已提供 |
| `analysis_empty.json` | 7 项指标全部数据不足，覆盖 5 种 reason | 最差情况 | ✅ 已提供 |
| `pose_window.json` | 姿态数据（约 50 帧） | 骨架叠加 | ⬜ 待补 |
| `task_progress.json` | 任务分阶段进度 | 上传进度页 | ⬜ 待补 |
| `session_draft.json` | 采集信息表单的待提交状态 | 表单页 | ⬜ 待补 |

> 已提供的三份在 `samples/fixtures/`。三份 `analysis_*.json` 都通过契约校验，
> 可直接用于开发报告页的全部三种数据状态。

### 3.2 为什么这 6 份是必需的

| fixture | 如果不做 |
|---|---|
| `analysis_normal.json` | 无法开发报告页 |
| `analysis_low_confidence.json` | 会忘记做 `?` 角标与警示文案——**而这正是产品区别于玩具的地方** |
| `analysis_insufficient.json` | 会忘记做"原因 + 改进建议"的占位块 |
| `analysis_empty.json` | 最容易被漏，**但这是最可能出现在真实场景里的状态**——教练第一次用 30fps 视频拍，所有时间类指标都不可用 |
| `pose_window.json` | 无法开发骨架叠加 |
| `task_progress.json` | 无法开发进度页 |

### 3.3 必须覆盖的 `insufficient.reason`

`analysis_insufficient.json` 至少要覆盖下列四种，因为它们对应的用户建议完全不同：

| `reason` | 界面文案 | 建议内容 |
|---|---|---|
| `low_frame_rate` | 拍摄帧率不够 | 改用慢动作模式重拍 |
| `view_mismatch` | 该指标需要另一种拍摄方位 | 补拍正面/背面视角 |
| `no_reference_scale` | 缺少参考尺度 | 让跑道分道线入画 |
| `perspective_error` | 运动员偏离画面中心过远 | 跟踪时让运动员更靠画面中心 |

**这四种文案是 App 中最有价值的部分之一**——它们直接教育教练下次怎么拍。

## 4. Fixture 的三个坑

### 坑一：用随机数生成

```dart
// ❌ 绝对不要
angle: Random().nextDouble() * 180
```

| 问题 | 说明 |
|---|---|
| 每次运行不同 | 无法写 UI 快照测试 |
| 语义错误 | 会生成 `173.4°` 这种看似合理但物理上不可能的膝角 |
| 掩盖问题 | 界面照常渲染，你不会发现缺少合理性检查 |

**正确做法**：手写固定的 fixture JSON，或在 Dart 里写死字面量常量。

### 坑二：fixture 过度理想化

如果所有 fixture 都是"全部正常"，你会忘记做低置信和数据不足的界面。

**要求：`analysis_low_confidence.json` 和 `analysis_empty.json` 必须在第一周就做出来，不能等到"以后补"。**

### 坑三：数值不真实

手写 `触地时间: 9999ms`，界面不会有任何反应——它会照常渲染成一个进度条。

**正确做法**：fixture 里的数值应当**语义合理但来源明确是假的**，并在文件头加注释：

```json
{
  "_fixture": true,
  "_comment": "手工编写的测试数据，非真实测量值",
  "_authored_at": "2026-02-11",
  "_schema_version": "1.0.0",

  "metric_id": "ground_contact_time",
  "value": 183.0,
  "unit": "ms",
  "ref": { "low": 160.0, "high": 220.0 }
}
```

### 3.4 数值的合理范围（供手写 fixture 参考）

> **这些是语义合理性检查用，不是标准值。**
>
> 真正的标准值必须查文献（见 `04-参考标准值规范.md`），**不得从下表推断**。

| 指标 | 合理量级 | 说明 |
|---|---|---|
| 膝角 | 40–180° | 超过 181° 不可能 |
| 髋角 | 90–182° | — |
| 着地胫骨角 | −20–40° | 负值表示膝在踝后方 |
| 躯干前倾角 | 0–70° | 加速段可到 60°；途中跑应 5–15° |
| 步频 | 120–300 步/分 | 超过 300 不可能 |
| 触地时间 | 80–250 ms | 短跑应 < 150 ms |
| 腾空时间 | 80–200 ms | — |
| 占空比 | 0.2–0.6 | 短跑应 < 0.5 |
| 骨盆倾斜角 | −15–15° | 额状面 |
| 着地膝内扣角 | 0–25° | 额状面，正值表示内扣 |

**fixture 中出现的数值超出这些范围时，应当是有意为之**（用于测试界面的异常处理），且需在 `_comment` 中说明。

## 5. 关键帧图片的处理

### 5.1 问题

关键帧图需要**真实的跑道背景 + 骨架叠加**。但没有真实视频就没有真实图片。

### 5.2 解决方案：免费素材图 + 程序化画骨架

| 步骤 | 做法 |
|---|---|
| 1 | 从免费图库找侧面跑步照片（注意授权） |
| 2 | 在图上手工确定 16 个关键点的像素坐标 |
| 3 | 把这 16 个坐标写入 `pose_window.json` 的对应帧 |
| 4 | App 用 `CustomPaint` 按 fixture 坐标画骨架 |

**关键：骨架是画上去的，不是 P 上去的。**

这样做的收益：

| 收益 | 说明 |
|---|---|
| 图上每个点都与 fixture 数据一致 | 改 fixture 图就跟着变 |
| 可以测试三种状态 | 把某些点的 `q` 改成 0，验证空心/不绘制的效果 |
| 接后端时无缝替换 | 只是把背景图从 assets 换成服务端 URL |

### 5.3 需要准备的素材图

| 文件 | 视角 | 用途 |
|---|---|---|
| `assets/samples/side_run.jpg` | 侧面 | 侧面视角关键帧 |
| `assets/samples/front_run.jpg` | 正面 | 额状面关键帧 |

**授权要求**：必须使用可商用的免费图库（如 Unsplash、Pexels），并在 `assets/samples/CREDITS.md` 中记录来源与授权。

### 5.4 尺度条的画法

`09-报告与指导解析规范.md` §3.3 要求每张关键帧图必须画尺度条。

在 fixture 阶段，尺度条直接用 `keyframes[].pixels_per_meter` 的值绘制：

```dart
// 画 0.5 m 的尺度条
final barWidthPx = 0.5 * keyframe.pixelsPerMeter * canvasWidth;
```

**注意**：归一化坐标下需要乘以画布宽度换算为实际像素。

## 6. App 各模块对后端的依赖度

> **这张表决定了 App 开发的推进顺序。**

| 模块 | 依赖后端 | 现在能做 | 说明 |
|---|---|---|---|
| 项目骨架、导航、路由 | ❌ | ✅ 立即 | — |
| 契约模型生成 | ❌ | ✅ 立即 | 从 Schema 生成 |
| 视频选择（SAF） | ❌ | ✅ 立即 | 纯客户端 |
| 视频元数据读取 | ❌ | ✅ 立即 | Platform Channel |
| App 端初级校验 | ❌ | ✅ 立即 | 帧率自洽性检查 |
| 采集信息表单 | ❌ | ✅ 立即 | 只写数据 |
| **上传（分片续传）** | ⚠️ | ✅ 可做 | 用本地 Mock 服务端接收 |
| 任务进度页 | ⚠️ | ✅ 可做 | fixture 驱动 |
| **报告页** | ❌ | ✅ 立即 | fixture 驱动 |
| 关键帧骨架叠加 | ❌ | ✅ 立即 | fixture 坐标 + 素材图 |
| 指标对比图 | ❌ | ✅ 立即 | fixture 驱动 |
| 指导解析卡片 | ❌ | ✅ 立即 | fixture 驱动 |
| 运动员列表 / 历史 | ⚠️ | ✅ 可做 | 本地 SQLite 先顶上 |
| 账号体系 | ✅ | ⏸ 延后 | 需要服务端 |
| 推送通知 | ✅ | ⏸ 延后 | 需要服务端 |

### 6.1 结论

**App 的 90% 可以零后端完成。**

唯一需要后端的两项（账号、推送）都属于 P8 阶段，不影响核心流程。

### 6.2 上传的 Mock 方案

上传模块需要一个接收端才能测试。两个选择：

| 方案 | 说明 |
|---|---|
| **本地 Mock 服务端** | 一个 30 行的 Python/Node 脚本，接收分片、写文件、返回假 task_id | 
| 直接存本地 | 把"上传"实现为写本地文件，接后端时替换实现 |

**推荐本地 Mock 服务端**：它能真实测试分片、断点续传、超时重试这些容易出问题的逻辑，而这些逻辑如果只写不测，接后端时会集中爆发。

## 7. 推荐的开发顺序（两周）

### 第 1 周：地基

| 天 | 任务 | 产出 |
|---|---|---|
| 1 | Flutter 项目初始化 + 目录结构 + Riverpod 配置 | 可运行的空壳 |
| 2 | **写 `gen_models.py`**，从 Schema 生成 Dart 模型 | `lib/models/*.dart` |
| 3 | 手写三份 fixture（normal / low_confidence / insufficient） | `assets/fixtures/` |
| 4 | `AnalysisRepository` 抽象 + `FixtureDataSource` | 能读到数据 |
| 5 | 领域模型映射层（契约模型 → 界面模型） | 界面不直接消费契约模型 |
| 5 下午 | ★ 逐字段核对契约，**记录每个字段的消费方式** | **契约问题清单** |

> **第 5 天下午这一步是本周最有价值的产出。**
>
> 它会暴露契约的问题：某个字段 UI 需要但契约没有、某个字段语义不清、某个枚举缺值。**发现问题要立刻改契约（升 Minor 版本），不要绕过、不要将就。**
>
> 这就是"先做 App 是验证契约最便宜的方式"——写后端时契约是你自己写自己用，你不会发现自己漏了什么。

### 第 2 周：报告页

| 天 | 任务 | 依据 |
|---|---|---|
| 1 | 报告页骨架 + 头部 + 总览 | `09-报告规范` §3.1–3.2 |
| 2 | 指标对比图（横向条形 + 区间底色 + 视角分组） | `09-报告规范` §3.4 |
| 3 | 指导解析卡片（含处方与口令） | `09-报告规范` §3.5 |
| 4 | **三种数据状态的视觉处理** | `08-App规范` §4 |
| 5 | 关键帧骨架叠加（CustomPaint + 尺度条） | `08-App规范` §6.2 |

> **第 4 天不要往后拖。** 三种数据状态是产品区别于玩具的地方。等 UI 都做完再补，会变成贴膏药——所有组件都要改。

## 8. 检查清单

**App 开发阶段（无后端）完成时应满足：**

- [ ] 模型由 Schema 生成，非手写
- [ ] `AnalysisRepository` 有抽象接口与三种实现
- [ ] 6 份必需 fixture 全部存在，且通过 Schema 校验
- [ ] `analysis_empty.json` 已产出（最易漏但最可能出现）
- [ ] 四种 `insufficient.reason` 的文案都已实现
- [ ] 切换 `--dart-define=ENV` 可无痛切换数据源
- [ ] 业务代码中**没有任何**直接 `import` fixture 的地方
- [ ] 关键帧骨架由 fixture 坐标绘制，非手绘
- [ ] 素材图授权已记录在 `CREDITS.md`
- [ ] 契约问题清单已产出并反馈
- [ ] 至少 3 个 UI 快照测试（正常 / 低置信 / 数据不足）

**最关键的一条：**

> **业务代码中不得出现任何 fixture 相关的 import。**
>
> 如果报告页里写着 `import '../fixtures/analysis_normal.dart'`，说明数据源抽象没做到位，接后端时必然返工。
