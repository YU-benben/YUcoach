## 2. 本轮（第 6 轮）做的：抗噪性分析与一个隐藏很深的缺陷

### 动机：没有合规素材，怎么知道数值准不准

目标里要求"用真实训练视频验证"。但现有素材 30 fps，
所有指标被帧率门槛正确拦下 —— **真实素材上一个数值都算不出来**。

所以换一个角度：**人为地给解析解加噪声**，观察指标偏离真值多少。
这给出的是"误差上界"：只要真实关键点的抖动不超过注入幅度，
指标精度就不会差于分析结果。

```
噪声档位     0px    1px    3px    6px   12px
（按 960 像素宽画面换算）
```

### 结果（修正合成模型后）

| 指标 | 3px 噪声下误差 | 相对 |
|---|---|---|
| `trunk_lean` | 0.03° | 0.4% |
| `hip_angle_toeoff` | 0.20° | 0.1% |
| `step_frequency` | 0.20 步/分 | 0.1% |
| `shank_angle_touchdown` | 0.35° | 0.4% |
| `knee_angle_touchdown` | 0.60° | 0.5% |
| `knee_angle_midstance` | 0.85° | 0.6% |

**结论：运动学角度指标对关键点噪声不敏感**，
3 像素抖动带来的误差都在 1° 以内。

### ⚠️ 但分析过程中发现了一个隐藏很深的缺陷

第一次跑出来的结果是这样的：

```
knee_angle_midstance   误差从 0 直接跳到 5.10，之后几乎不涨
```

**这个形状不对劲。** 误差应该随噪声单调增长，而不是"跳一下然后不动"。

追查下去，发现了三层问题：

#### 第一层：我的诊断建在退化输入上

合成跑者的骨盆高度是**恒定**的（振幅 0.00000）。
而"支撑中期 = 髋高局部最低点"这个判据，需要髋高有起伏才有信号 ——
在一条直线上找极值，检出的全是伪事件。

**教训：验证脚本的输入必须让被验证的判据有信号可用。**

#### 第二层：我的合成模型频率错了

给骨盆加上起伏后，步频算出 390 步/分（真值 273）。

根因是构造写成了 `bob = cos(2 * phase)`，而 `phase` 定义的已经是
**步**周期 —— 乘 2 得到的是跨步节奏，骨盆起伏频率变成两倍步频。
极值检测于是在错误的频率上找事件。

改成 `cos(phase)` 后立刻正确（频域 272.07 / 时域 271.70，真值 272.7）。

**这个 bug 本身不值得记，但它暴露的真实风险值得**：
若真实素材里骨盆信号的 2f 分量强于 f 分量，频域法同样会报出 2 倍步频。
**这正是本项目坚持两法交叉验证的理由** —— 频域法错 2 倍时时域法是对的，
两者一比就露馅。

#### 第三层：这才是真正的算法缺陷 ⚠️

修正前两层后，支撑中期的误差仍然反常。用直接测量查事件帧的稳定性：

| 噪声 | 支撑中期帧号偏移（中位） |
|---|---|
| 1 像素 | **67 帧** |
| 3 像素 | 106 帧 |
| 6 像素 | 120 帧 |

而**真值事件的间隔只有 53 帧** —— 也就是说检出点**整整错了一个步态周期**。

根因：髋高的垂直起伏（跑步时 5–10 cm）远小于腿部摆动等其他运动的幅度，
所以髋高曲线在最低点附近**很平**。在平坦的极小值上定位，
噪声稍微一推，检出点就滑到相邻周期去了。

**修法不是"把极值找得更准"，而是加物理约束**：

> 支撑中期按定义就落在支撑期内 —— 即触地与离地之间。
> 触地/离地由踝高判定，在同样噪声下稳定得多（偏移 < 1 帧）。
> 于是在 `[触地, 离地]` 区间内找髋高最低点。

用**可靠的测量去约束不可靠的测量**。效果：

| 噪声 | 修正前 | 修正后 |
|---|---|---|
| 1 像素 | 67 帧 | **0 帧**（均值 0.07） |
| 3 像素 | 106 帧 | 0.28 帧 |
| 6 像素 | 120 帧 | 0.94 帧 |

端到端效果：`knee_angle_midstance` 在 1 像素噪声下的误差
**从 5.10° 降到 0.25°**。

#### 顺带修的两处

在排查过程中还发现 `_local_extrema` 两个独立问题，都已修正：

1. **平台未折叠**：判据 `z[i] >= z[i-1] and z[i] >= z[i+1]` 会把一段
   等高平台上的每个点都列成候选，而显著性分数在平台上几乎相同 ——
   选哪个取决于排序的稳定性。现在识别平台并取**中心**。
2. **显著性窗口硬编码 5 帧**：240 fps 下只占步周期的 2%，60 fps 下占 8%。
   同一个算法在不同帧率下行为不同。现在窗口按 `min_gap` 缩放。

### 新增回归测试

`backend/tests/test_phase_robustness.py`（10 条）。
这类缺陷**不会让任何测试失败、不会报错、不会产生非法值** ——
它只是让指标悄悄变差。没有专门针对"抗噪性"的测试就发现不了。

### 这个分析的边界（必须说清）

- 它给的是**误差上界**，不是真实精度。注入的是零均值噪声，
  只造成随机误差；真实误差还包含模型的系统性偏差。
- 真实素材的遮挡、运动模糊、透视变形，都不是高斯噪声能模拟的。
- 合成模型已知局限（会让误差**偏乐观**）：
  `knee_angle_touchdown` 与 `knee_angle_midstance` 的真值相同（都是 121.1°），
  而真实跑步中两者相差约 30° —— 合成腿缺少着地缓冲的屈膝动作。

**所以：结论只能用来判断"哪些指标对噪声敏感"，
不能当作真实精度引用，更不能替代用真实素材做的精度验证。**

## 3. 第 5 轮做的：文献检索与防错机制

### 标准值从 1 条增加到 5 条

找到了一份**口径完全匹配**的权威数据源：

> **IAAF《2017 伦敦世锦赛生物力学报告》男子 100m 决赛**
>
> 这类官方生物力学报告的价值：受试者是当场成绩最好的 8 个人，
> 测量手段是高速摄影（非激光、非加速度计），
> 且**报告了逐运动员的原始关节角度** —— 与本项目的测量方式最接近。

新增 4 条：

| 指标 | 区间 | n | 口径 |
|---|---|---|---|
| `knee_angle_touchdown` | 133.1–166.7° | 14 | ✅ 完全一致 |
| `ground_contact_time` | 85–118 ms | 3 | ⚠️ 取自倒数第二步 |
| `flight_time` | 125–145 ms | 3 | ⚠️ 同上 |
| `step_length_relative` | 1.08–1.20 | 8 | ✅ 完全一致 |

**换算过程写成了可复核的脚本**（`scripts/literature/verify_iaaf_standards.py`）——
手算出来的数字无法查证，等同于编造。

### ⚠️ 主动拒绝了一份数据

`trunk_lean` 的检索**找到了数据，但决定不用**。

从报告 Table 10 提取的躯干角，按原文口径（相对水平，直立为 90°）
换算出 **61–68° 的前倾角**。但短跑途中跑应接近直立。

矛盾触发核查，结论：

1. 报告自己承认该角度**不含脊柱弯曲与躯干旋转**，
   而这两者在冲线阶段"quite prominent"
2. Figure 21 的纵轴范围是 **45–90°**，报告的是倒数第二步与冲线时刻
3. 61–68° 的前倾角意味着躯干几乎水平 —— 那是起跑前三步的姿态

**口径未核实前不得入库**（`docs/04` §4.3）。这条被记进
`iaaf_2017_100m.yaml` 的 `rejected` 段，连同完整理由 ——
比单纯留空更有价值：它防止后来的人重复检索同一份材料。

**顺带发现更重要的事**：本项目文档里写的
「加速段 45–60° 是优秀」「途中跑 5–15° 才对」
**同样没有可靠出处**。那两条也是二手转述，不能采信。

### 新加的三道防错机制

这轮的价值不止"多了 4 条标准值"，更在于**让同类错误以后无法再发生**。

#### ① 生理可信范围检查

上面那个「61–68° 前倾角」为什么危险？
因为它**在 0–180° 的合法角度范围内毫无问题** ——
只有对照"人跑起来躯干能摆成什么样"才能发现它错了。

所以给每个指标声明了 `plausible_range`，加载标准值时对照检查。
超出范围的值**被拒绝加载**，并提示"这通常意味着从文献提取时取错了行/列"。

#### ② 单位核对

文献报告时间常用**秒**（0.101），本项目用**毫秒**（101）。
不换算的话，规则引擎会拿 0.101 去和实测的 101 ms 比，
判出"触地时间比参考值低 100 倍"。

**这类错误无法通过"看数值是否合理"发现** —— 0.101 是个完全正常的数字。

做法：YAML 里必须写换算后的值，加载器核对
"原值 ×1000 是否仍在可信范围内"。这能同时发现
**忘了换算**与**换算两次**（85000 ms）两个方向的错误。

#### ③ 规则与标准值的相位一致性

`verify_rules_e2e.py` 抓到一条真实缺陷：

```
规则 knee_angle_touchdown_too_high 声明 phase="acceleration"
标准值（IAAF）    实际是            phase="max_velocity"
```

运行时的相位匹配把它拦下了 —— 表现只是"这条规则从来不生效"，
**没有任何报错**。已修正规则声明并把这条不一致写进注释。

## 4. 第 4 轮做的：规则引擎数据化

### 标准值从代码里搬进了 YAML

上一轮的 `rules.py` 把标准值硬编码在 Python 里，只是 `citation` 留空。
本轮改成从 `data/standards/*.yaml` 加载，并加了**机械校验**。

**为什么这个改动比"多补几个数字"重要得多**：

`docs/04-参考标准值规范.md` §1 里写着：

> 标准值编造是**全项目唯一无法通过测试发现的错误类型**。
> 指标算错可以对比真值，契约写错有 Schema 校验，
> 规则写错有用例验证 —— 而标准值编造没有任何自动检测手段。

搬进 YAML 之后，这个缺口被补上了：

| 校验 | 拦住什么 |
|---|---|
| `metric_id` 必须在指标清单里 | 拼写错误、已删指标残留 |
| `source.locator` 必须非空 | **凭印象编造**（铁律的核心） |
| `view` 必须与指标适用视角一致 | 跨视角套用（几何量完全不同） |
| `phase` 必须合法 | 跨阶段套用（数值含义可能相反） |
| `measurement_note`/`extraction_note` 必填 | 口径未核对就入库 |

不合规的条目**被拒绝加载**，并在门禁 G4 里报错。

### 本轮实际核实的一条标准值

只填了**一条** —— 只有这一条真正读过原文、能指向具体表格：

```
step_frequency（100m 全程平均）
  区间 259.4–283.8 步/分  (mean 271.8, sd 12.0, n=8)
  出处：《Bioengineering》2023，柏林世锦赛 100m 决赛选手数据（Table 1）
```

提取过程中的判断都记在 YAML 的 `measurement_note` 里：

- 原文报告的是**全程平均**步频（总步数 ÷ 比赛时间），不是途中跑瞬时值
  → 标为 `phase: whole_run`，不能直接当途中跑标准值用
- 原文用**激光测距**而非视频分析 → 跨方法比较，口径不同
- 原文只给 `mean ± sd`，区间是我按 `mean±sd` 推算的
  → 必须标注为推算，不得伪装成原文数据
- 样本只有 7 名决赛选手 → 不是"精英群体常见范围"，只能当数量级参考

**这些局限会随结论一起展示给教练**（`caveat` 字段），
而不是只在数据库里躺着一行小字。

### 其余 19 个指标：刻意留空，且写清了为什么

`pending` 清单逐个记录"需要什么数据、去哪里找、为什么现在没有"：

## 5. 第 3 轮做的：App 端接通

### 架构

```
手机 App                    电脑（分析服务）
┌──────────────┐            ┌─────────────────────┐
│ 选视频        │            │ /api/videos  收文件  │
│ 初级校验      │  上传      │ /api/analyze 提交    │
│ 填采集信息    │ ─────────► │ /api/jobs    查进度  │
│ 看进度        │            │                     │
│ 打开报告      │ ◄───────── │ 分析引擎（GPU）      │
└──────────────┘   轮询      └─────────────────────┘
```

**为什么必须这样分：** 一段 5 秒的慢动作视频有上千帧，
逐帧 YOLO 推理在手机上要几分钟且会烫手降频。
分析放在电脑上、手机只负责拍摄与查看，是这个场景下的唯一合理解。

### 服务端：零依赖

用标准库 `http.server` 手写，**没有引入任何 Web 框架**。

理由：服务端只是"收文件 + 调引擎 + 返回 JSON"的壳，
真正的逻辑全在 `backend/analysis` 里。
装 FastAPI 会引入 pydantic / starlette / uvicorn 一串依赖，
而它们默认都往系统盘写缓存 —— 本项目的开发机上系统盘很紧张。

### 客户端的关键取舍

**① 用流式上传，不把视频读进内存**

慢动作素材常有几百 MB。`file_picker` 的 `readAsByteStream()`
配合 `http` 包的 `StreamedRequest` 让内存占用与文件大小无关。
一次性读进内存在中低端机上会 OOM，而 OOM 发生在上传阶段
会让用户完全摸不着头脑。

**② 上传与分析分开显示进度**

上传慢是网络问题（换个位置、缩短片段），
分析慢是算力问题（服务端在忙，只能等）。
混成一根进度条会让用户无法判断该不该继续等。

**③ 先存本地记录再上传**

如果上传或分析失败，记录仍在，教练能在「数据」页看到
并知道发生过什么。反过来先上传后记录，中途失败就什么都不剩，
而用户已经等了几分钟。

**④ 用轮询而不是 WebSocket**

分析只需几十秒。轮询实现简单，且**断线恢复自然** ——
重连后继续查同一个 jobId 即可。长连接的保活与重连逻辑
在移动网络下容易出问题，而收益在这个场景里几乎为零。

## 6. 第 3 轮修的两个缺陷

### ① 路径穿越漏洞（安全）

`/api/analyze` 用调用方传来的 `video_id` 在上传目录里找文件。
最初的实现用 `UPLOAD_DIR.glob(f"{video_id}.*")` —— 这是错的：

```python
video_id = "/etc/passwd"     # glob 直接抛 NotImplementedError
video_id = "../../secret"    # 模式可能匹配到目录之外
```

服务默认监听 `0.0.0.0`（局域网可访问），所以这是**真实风险**：
局域网内任何人都能读到这台机器上的任意文件。

**修法不是"过滤危险字符"** —— 那种做法总会漏掉某种编码方式
（URL 编码、`....//`、Unicode 归一化、符号链接）。
改成两道白名单：

1. `video_id` 必须严格匹配 `^[0-9a-f]{16}$`（本服务自己生成的格式）
2. 只接受**上传登记表里记过的** id，用户输入完全无法影响文件路径

测试里覆盖了 5 种穿越载荷，并断言响应里不含目标文件的内容。

### ② 服务启动时因控制台编码崩溃

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'
```

Windows 默认 GBK 控制台，遇到 `⚠️` 直接崩在 `print` 上 ——
**服务根本起不来**，但所有单元测试仍然全绿
（测试是在进程内起服务的，绕过了真实启动路径）。

修了两处：
- 服务端加 `_init_console()`，与 `scripts/` 下的脚本统一处理
- 去掉 emoji，改用 `[WARN]` 这类纯 ASCII 标记

**并且新增了一道门禁 G5b**，专门补这个缺口：
真的把服务当**子进程**起起来，真的用 HTTP 打它的接口。
测试覆盖逻辑正确性，这道门覆盖"服务能被启动"本身。

### 顺带修的回归

重构 `analyze.py` 时（把核心逻辑抽成 `run_pipeline()` 供服务端复用），
`main()` 里遗留了一处对 `t_start` 的引用 —— 那是另一个作用域的局部变量。

这个错误被控制台编码问题盖住了：真正的 `NameError` 完全看不到，
只看到一个 `UnicodeEncodeError`。修掉编码问题后才暴露出来。

**教训：报错信息的可读性直接决定排查速度。**
一个把真实错误盖住的编码崩溃，比错误本身更耗时。

### 修正的一处文档错误

`docs/03-指标定义.md` 把 `stance_width_relative` 归入"需参考尺度"，
**这是错的**。它的计算式是：

```
|着地侧踝x − 对侧踝x| / 髋宽像素中位数
```

分子分母都是画面长度，换算成实际距离时**尺度因子会约掉**。
已改正文档并在代码里注明。实际影响不小 ——
它是额状面里少数几个在跟踪拍摄、没有参照物的素材上仍能用的指标。

### 关于第 2 项：为什么合成验证还不够

端到端验证证明了**计算逻辑正确**（数值与解析解一致），
噪声敏感性分析给出了**误差上界**（3 像素抖动下 <1°），
但两者都证明不了**真实精度** —— 因为：
- 合成数据的姿态是解析式生成的，没有真实的关键点抖动模式
- 没有真实的遮挡、运动模糊、透视变形
- 没有基准可比对（不知道模型的系统性偏差有多大）

要验证真实精度，需要两样东西：

1. **符合拍摄标准的素材** ——
   侧面固定机位 · 120 fps 以上 · 运动员占画面高度 1/3 以上 · 分道线入画
2. **人工标注的基准** —— 抽 20–30 帧手工标注 16 个关键点，
   量化模型误差（像素级）

现有素材（960×540、30 fps、跟踪拍摄）只能验证"链路通不通"：
**所有指标都被帧率门槛正确拦下了**，一个数值都算不出来。
