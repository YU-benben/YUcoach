## 0. 一句话

**你现在的瓶颈不是模型、不是算法、不是代码——是"没有一批合规素材 + 人工标注基准"。**

现有素材（960×540、30 fps、运动员占画面 13%）**所有指标都被帧率门槛正确拦下**（[docs/13](13-分析引擎实现进度.md) §8），真实精度一次都没验证过。

> ⚠️ **2026-10-13 的实测把这条结论坐实了，而且比原来更严重。**
>
> 目视核对时发现：模型在现有素材上检出的 4 个"人"**全是画面中部的远处行人**，
> 而真正的运动员（左下方、**起跑蹲踞**姿势）**一个都没检到**。
> 原因是 YOLOX 在直立人体上训练，对蹲踞姿态识别率低。
>
> 也就是说：**现有素材连"检测到运动员"这一步都做不到** ——
> 不只是"数值不准"，是根本没有可用的数值。详见 [docs/14](14-关键点模型选型对照表.md) §9.6。

**所以下一步只有一件事：拿到合规素材，标注 24 帧。**

## 2. 阶段 1 · 打地基（约 3 周）

> **目标：把"真实精度未知"变成"已知且可引用"。**
> 这一阶段的产出同时喂给三个目标：产品、论文、答辩。

### 步骤 1.1 · 补一条判据（1–2 小时）✅ 已完成 2026-10-13

**已实现为** [scripts/check_foot_scale.py](../scripts/check_foot_scale.py)

补的那条解剖学尺度自检——原有四条判据抓不到"足部点塌缩"这种失效模式：

```python
# 足长 ≈ 0.15 × 身高；躯干(肩中点-髋中点) ≈ 0.30 × 身高
ratio = dist(ankle, toe) / torso_height_px   # 合理区间 0.35 – 0.75
```

**依据**：与 [docs/02](02-数据标准.md) QC-2「肢长恒定 <3%」是同一思路——用解剖学常数约束测量结果。

**验收**：脚本能输出该比值的中位/分位数，并在超出区间时报出可疑帧号。

> ⚠️ **在现有素材上跑出来的数字不能用来判定模型好坏** ——
> 运动员躯干只有 17 像素、足长只有 6 像素，这个尺度下比值方差必然很大
> （实测范围 0.016 – 29.9）。**判据本身可用，但必须等合规素材才能定论。**
> 详见 [docs/14](14-关键点模型选型对照表.md) §9.7。
>
> **不要**据现在的数字去调 `RATIO_MIN` / `RATIO_MAX` —— 那等于按噪声调阈值。

**同时新增** [scripts/make_overlay.py](../scripts/make_overlay.py)（QC-4 叠加目视工具）：
把关键点画回原帧，并**裁剪足部区域放大 8 倍**。
这个工具立刻抓出了两个问题（选人缺陷 + 模型没检测到蹲踞的运动员），
见 [docs/14](14-关键点模型选型对照表.md) §9.6。

### 步骤 1.2 · 采集合规素材（半天到一天）⭐ 关键路径

**拍摄规格**（严格按 [docs/02](02-数据标准.md) §11）：

| 项 | 要求 | 为什么 |
|---|---|---|
| 帧率 | **120 fps 或 240 fps** | 触地 80–120 ms，30 fps 下无意义 |
| 机位 | 侧面固定机位，距跑道 8–15 m，高约髋高 1.0–1.3 m | |
| 画面占比 | 运动员占画面高度 **50–70%** | 现有素材只有 13%，是精度无法评估的直接原因 |
| 分道线 | **必须入镜** | 唯一的 A 级参考尺度（1.22 m 国标） |
| 快门 | ≥ 1/1000 s | 防运动模糊 |
| 曝光/对焦 | **锁定** | 自动会导致关键点随亮度漂移 |
| 电子防抖 | **关闭** | 会引入帧间几何变形，破坏逐帧尺度 |
| 时长 | 每段 3–5 秒 | 3 个完整步次即可 |
| **拍途中跑，不要拍起跑** ⭐ 新增 | 让运动员先加速，只拍途中跑段 | **模型对蹲踞姿态识别率低**，实测会漏掉蹲踞的运动员、检到远处的行人。见 docs/14 §9.6 |
| **画面里不要有其他人** ⭐ 新增 | 清场，或选无人的时段 | 现素材有多个行人，检测器与选人策略都会被干扰 |

**必须同时记录**（[docs/02](02-数据标准.md) §11.4 目前只要求了前两项）：

| 新增记录项 | 为什么现在就要记 |
|---|---|
| 站立点到跑道边缘的垂距 + 相机高度 | 相机位姿初值；**30 秒的事，事后补不回来** |
| 站在第几道延长线上（对齐哪条分道线） | 跑道坐标系原点 |
| 手机镜头大致朝跑道哪一端 | 消掉 180° 朝向歧义 |
| **这次跑的是什么速度**（低/中/最高） | 速度分层是论文题眼，见步骤 1.4 |

> ⚠️ **顺手做一次可行性试验（10 分钟，决定后两个阶段）**：
> 用一台手机静态侧向拍运动员跑 15–20 m，看**全身在多长距离内不出画**。
> 这个数字决定"跨视角定位"和"双机位"两条线是否可行。

**拍摄清单：**

- [ ] 侧面固定机位 × 3 段（不同运动员或不同速度）
- [ ] 正面 / 背面各 1–2 段（供额状面指标与左右侧校验）
- [ ] **同一段同时拍一个固定机位对照**（零成本，给透视误差一个真值）
- [ ] 记录机位参数（上表四项）
- [ ] 回放确认：无模糊、无失焦、分道线清晰、**画面里没有其他人**
- [ ] **回到电脑上先跑一次 `make_overlay.py` 确认检测到的是运动员** ——
      再决定要不要继续拍剩下的。这一步能省掉整批素材白拍的风险

### 步骤 1.3 · 人工标注（数天）⭐ 真正的瓶颈

**按 [docs/02](02-数据标准.md) §15.3 的既有规定做，不要另定标准：**

```
必须连续标注至少 3 个完整循环 —— 每侧 12 帧，共 24 帧
每个循环标 4 帧：touchdown / midstance / toe_off / swing_peak
```

**然后走完你已有的四道 QC：**

| QC | 内容 | 目标 |
|---|---|---|
| QC-1 | 组内信度（**7 天后**重标 15 帧） | 关键点平均像素距离 < 5 px @1080p |
| QC-2 | 几何一致性（自动） | 肢长变异 < 3% |
| QC-3 | 生理合理性（自动） | 各关节角落在合理区间 |
| QC-4 | **叠加目视** | 唯一不能自动化的环节 —— 工具已就绪（`make_overlay.py`） |

**输出**：`<session_id>_keypoints.csv`（50 列）、`<session_id>_events.csv`

**清单：**

- [ ] 标注 24 帧 × 16 关键点（遮挡处留空，不猜）
- [ ] 事件表（触地/支撑中期/离地/摆动最高）
- [ ] QC-2 / QC-3 自动检查通过
- [ ] QC-4 目视通过（**看对象对不对，不只是形状对不对**）
- [ ] QC-1 安排 7 天后执行

### 步骤 1.4 · 多模型横向评测（1 周）

**这是论文的核心，也是产品选型的依据。**

| 模型 | 类别 | 状态 |

| MediaPipe 33 | 端侧轻量 | ✅ 已装已缓存（评估脚本已有，未接主流程） |

| RTMW | 全身 | 需接入 |
| YOLOv8-pose | 检测范式基线（默认） | ✅ 在用 |

**评测指标：**

| 指标 | 分档 |
|---|---|
| 关键点像素误差 | 躯干 / 大腿 / 小腿 / **足部** |
| 关节角度误差 | **SEM**，对标公开水平 <5° |
| **足部尺度比值通过率** | 步骤 1.1 那条判据（`check_foot_scale.py`） |
| **速度分层** ⭐ | 低速段 / 中速段 / 最高速段分别报 |
| 左右侧一致性 | 正面 / 背面各测 |

> ⭐ **速度分层是你的题眼。** Theia3D 那篇在有标记点的三维场景已发现"最高速触地时差异变大"；
> **在单目 2D 场景验证同一条规律，公开文献里没人做过。**

**清单：**

- [ ] 按速度分层统计

### 步骤 1.5 · 决策门（阶段 1 结束）

```
            角度误差是否接近 SEM < 5°？
                    ↓
        ┌───────────┴───────────┐
       是                      否
        ↓                       ↓
  模型冻结，进入阶段 2      先查拍摄问题（模糊/占比/曝光）
```

### 4.1 让机位参数真正参与计算 ⭐ 最低成本的实质改进

**改动**：把透视误差从档位常量换成几何量。


**为什么优先做这个**：不需要分道线、不需要标定、不需要新素材，用现有 30 fps 素材就能跑通并写测试，直接替换那个硬编码。

## 5. 阶段 4 · 更强的论文（可选，取决于精力）

| **B. 双机位三维 + OpenCap 对照** | 数周 | 精度上限参照，但 5 m 距离限制与短跑冲突（见下） |
| **C. 跨视角定位（跑道单应）** | 数月 | 解锁绝对速度、步幅米数——**但见 §6 暂缓项的判断依据** |

### 5.1 关于 B（双机位 / OpenCap）的现实判断

| 约束 | 影响 |
|---|---|
| OpenCap Monocular 要求相机距人 **< 5 m**、全身始终在框 | ❌ **与 100 m 冲刺直接冲突** |
| 已验证活动仅**坐立/步行/深蹲** | 短跑未验证 |
| 官方明说跳跃"不支持且不可靠" | 高速动作风险高 |
| 云端 App 仅 iOS；本地管线支持任意来源 | 可绕开，但需 ≥8 GB 显存（你有） |

**结论：先走 [SimTK 公开数据集](https://simtk.org/projects/opencap)**（免费、带金标准、含视频+动捕+GRF+EMG），用它：
1. 验证你的算法实现
2. 校准误差预期
3. 给开题的"数据来源"一节提供依据

**不要**先花时间搭 OpenCap 采短跑数据——设计前提与短跑冲突。

### 5.2 关于 C（跨视角定位）

**判断依据已经明确，等 §2 步骤 1.2 的"10 分钟可行性试验"结果：**

```
全身在多长距离内不出画？
        ↓
   ≥ 15 m              < 10 m
      ↓                   ↓
  值得做              不值得做
（分段分析可行）    （只能覆盖极少步次）
```
